# Experiment 020-C: Declarative Rule and Expression Engine

## 1. What were we trying to prove?

### In simple terms

In 020-A and 020-B.1, FORGE learned how to understand a specification and determine whether requested capabilities are available.

But specifications don't just say:

> "Generate a number."

They also need to express things like:

```text
NET_AMOUNT = SUBTOTAL - DISCOUNT
```

or:

```text
IF CUSTOMER_TYPE = "PREMIUM"
THEN CREDIT_LIMIT >= 5000
```

or:

```text
COUNTRY IN ["US", "UK", "IN"]
```

So we asked:

> **Can FORGE understand and evaluate declarative rules and expressions without requiring custom Python code for every rule?**

# 3. What happened?

Most individual expressions worked.

```text
19 / 22 tests passed
```

Three expressions failed:

```text id="wsmu2q"
CMP-003   Amount between bounds
STR-004   Regex validation
NEST-001  Premium high-value rule
```

The experiment therefore ended:

```text id="6t8vdy"
Tests passed:  19/22
Tests failed:   3/22
Overall:       FAIL
```

---

# 4. What does that actually mean?

This is where the result gets interesting.

At first glance, **19/22 looks pretty good**.

But we should not call this a successful generic expression engine.

Why?

Because the three failures aren't just cosmetic examples. They expose weaknesses in increasingly important capabilities:

### Failure 1: BETWEEN

The engine could handle simple comparisons, but failed to correctly evaluate:

```text
value BETWEEN minimum AND maximum
```

That means the engine's handling of compound comparison semantics isn't completely reliable.

### Failure 2: Regex / MATCH

The rule vocabulary includes string matching, but the actual validation behavior did not match the expected result.

That tells us that having an operator named `MATCH` in the vocabulary isn't sufficient. Its semantics need to be precisely defined and tested.

### Failure 3: Nested expression

This is probably the most architecturally significant failure.

The rule:

```text
Premium AND
    High Value
```

was represented as a nested expression and failed.

That means we cannot yet confidently say:

> "FORGE can evaluate arbitrary declarative expressions compositionally."

And **that is exactly what a generic rule engine needs to do.**

---

# 5. Why is this different from 020-B?

This is an important distinction for the final architecture document.

### 020-B

```text
TRANSFORM
   ↓
Registered?
   YES

Executable?
   NO

Result:
   BLOCK
```

This was a **capability availability problem**.

### 020-C

```text
BETWEEN
   ↓
Registered?
   YES

Executable?
   YES

Correctly evaluates?
   NO
```

This is a **semantic correctness problem**.

So we're discovering another layer:

```text id="i1h1kf"
Vocabulary
    ↓
Capability exists
    ↓
Implementation exists
    ↓
Implementation behaves correctly
    ↓
Implementation composes correctly
```

020-B.1 addressed the first few layers.

020-C shows we need to validate the last two.

---

# 6. What did the experiment teach us?

The biggest learning is:

> **A declarative rule engine cannot be considered complete merely because its operators are registered or individually executable. It must also have correct semantics and support composition of expressions.**

This is especially important for FORGE because eventually we want specifications such as:

```text
IF
    CUSTOMER_TYPE = PREMIUM
    AND
    ORDER_VALUE > 5000
THEN
    DISCOUNT >= 5
```

That is not one primitive operation.

It is a tree:

```text
                IF
                 │
          ┌──────┴──────┐
          │             │
        AND           DISCOUNT
       /   \             >= 5
      /     \
 PREMIUM   ORDER_VALUE
   =       > 5000
```

If nested expression evaluation isn't reliable, the declarative specification becomes unreliable.

---

# 7. What did we NOT prove?

020-C does **not** establish that:

* all 41 executable operators are correct
* nested expressions are reliable
* complex rules can be safely composed
* expression evaluation is production-ready
* derived fields can be evaluated generically
* expressions can participate safely in dependency planning
* constraints based on expressions can be enforced during generation

Those capabilities remain open.

---

# 8. Architectural Outcome

The experiment exposed the need for a proper **expression evaluation layer**, rather than treating rules as a collection of independent functions.

The architecture is moving toward:

```text id="9jy1w0"
Declarative Rule
       │
       ▼
Expression Parser
       │
       ▼
Expression Tree / AST
       │
       ▼
Semantic Evaluation
       │
       ▼
Typed Result
       │
       ▼
Validation
```

This is an important architectural direction.

The rule:

```text
A AND B
```

should not simply be interpreted as "call function AND."

FORGE needs to understand:

```text
AND
├── evaluate A
└── evaluate B
```

That becomes especially important when we later combine rules, constraints, conditions, derivations, and statistical relationships.

---

# 9. Resulting FORGE Capability

The result should **not** be phrased as:

> FORGE has a generic expression engine.

That would overclaim.

Instead:

> **FORGE has established a declarative rule vocabulary and executable expression framework, but 020-C exposed semantic and nested-expression correctness gaps that must be resolved before the rule engine can be considered reliable.**

That is a much more defensible outcome.

# 11. Architectural Evolution

This gives us another useful chain:

```text
020-B
Generic generation
     │
     │ FAIL
     ▼
Registered capability ≠ executable capability
     │
     ▼
020-B.1
Capability assessment
     │
     │ PASS
     ▼
Safe execution planning
     │
     ▼
020-C
Rule / expression execution
     │
     │ FAIL
     ▼
Capability ≠ semantic correctness
```

So we're learning something important about FORGE:

> **Every layer needs to be validated independently before it is allowed to become an assumption underneath the next layer.**

I would definitely preserve the **19/22 failure** in the final 020 document. It demonstrates that the experiments are genuinely finding architectural weaknesses rather than being designed to produce a sequence of convenient PASS results.

And I would expect the next work around rules to eventually revisit these failures before we declare the expression layer production-ready.
