# Experiment 020-M: Declarative Statistical Generation

## 1. What were we trying to prove?

### In simple terms

Consider a field such as:

```text
CUSTOMER_SCORE
```

A generic random generator might produce:

```text
12
87
43
91
...
```

But real data usually has a statistical shape.

For example:

```text
AGE
```

might approximately follow a normal distribution.

A transaction quantity might follow something closer to a Poisson distribution.

A categorical field might have:

```text
STANDARD   70%
PREMIUM    20%
SPECIAL    10%
```

So the question becomes:

> **Can FORGE express and execute statistical generation declaratively, rather than hard-coding a generator for each field?**

---

# 2. The architecture tested

The experiment establishes a clean pipeline:

```text
Declarative field specification
          ↓
Distribution analysis
          ↓
Parameter validation
          ↓
Statistical generator
          ↓
Statistical validation
```

That separation is important.

The specification says **what distribution is required**.

The runtime determines **how to generate it**.

---

# 3. What distributions are currently executable?

Five distributions are currently implemented:

```text
CATEGORICAL
DISCRETE_UNIFORM
NORMAL
POISSON
UNIFORM
```

The specification vocabulary is broader than the runtime.

These are currently deferred:

```text
BETA
EMPIRICAL
EXPONENTIAL
GAMMA
LOGNORMAL
MIXTURE
TRIANGULAR
TRUNCATED
WEIBULL
```

This is actually a good architectural outcome.

We are deliberately maintaining:

```text
Registered capability
        ≠
Executable capability
```

which we already established in 020-B.1.

# 5. What does this actually prove?

The key result is:

> **FORGE can generate statistically shaped data from declarative distribution specifications using an explicit, validated parameter model.**

For example, conceptually:

```text
CUSTOMER_SCORE

distribution:
    NORMAL

parameters:
    mean = 70
    stddev = 10
```

means the generator isn't simply doing:

```text
random number between 0 and 100
```

It is producing values according to the specified statistical model.

---

# 6. Why parameter explicitness matters

This test passed:

> **Parameter explicitness: PASS**

That's important.

We don't want something like:

```text
distribution = NORMAL
```

and then FORGE secretly invents:

```text
mean = 50
stddev = 15
```

That would make the result difficult to reproduce and impossible to explain.

Instead:

```text
Distribution
     +
Explicit parameters
     ↓
Deterministic generation given seed
```

The specification remains the source of truth.

---

# 7. Parameter validation also passed

A distribution is not useful unless its parameters make sense.

For example:

```text
NORMAL
mean = 70
stddev = -10
```

is invalid.

Similarly, a categorical distribution cannot have:

```text
values = [A, B, C]
weights = [0.5, 0.5]
```

because the two arrays don't match.

020-M validates the distribution configuration before execution.

This is important because otherwise bad statistical specifications could produce misleading datasets.

---

# 8. No hidden distribution fallback is especially important

This test passed:

> **No hidden fallback: PASS**

Suppose the specification asks for:

```text
LOGNORMAL
```

but the current runtime doesn't support it.

A dangerous implementation might silently do:

```text
LOGNORMAL
   ↓
Not implemented
   ↓
UNIFORM
```

The dataset would still be produced.

It might even look reasonable.

But it would violate the specification.

FORGE instead maintains an explicit capability boundary:

```text
Requested distribution
        ↓
Supported?
   ┌────┴────┐
   │         │
  YES        NO
   │         │
   ▼         ▼
Generate    DEFER / BLOCK
```

That's the correct behavior for a controlled synthetic-data engine.

---

# 9. Why reproducibility matters here

Statistical generation introduces randomness.

So:

```text
Specification
+
Distribution parameters
+
Seed 42
```

must produce the same result every time.

The experiment confirms:

> **Reproducibility: PASS**

At the same time:

> **Seed sensitivity: PASS**

means changing the seed produces a different sample.

So we have:

```text
Same specification + same seed
          ↓
       same data

Same specification + different seed
          ↓
       different data
```

That gives us controlled stochasticity.

---

# 10. Field-order independence passed

This is another important consistency property.

If:

```text
CUSTOMER_SCORE
UNIT_PRICE
QUANTITY
```

is reordered as:

```text
QUANTITY
CUSTOMER_SCORE
UNIT_PRICE
```

the statistical stream assigned to each field should not change merely because the declaration order changed.

The experiment confirms:

> **Field-order independence: PASS**

This connects directly to the field-level deterministic stream isolation established earlier.

---

# 11. What did we learn?

The key architectural learning is:

> **Statistical generation should be a declarative capability with explicit distribution vocabulary, explicit parameters, independent validation, and a hard boundary between executable and deferred distributions.**

That gives us a clean statistical layer:

```text
                 Field Specification
                        │
                        ▼
                 Distribution
                        │
                        ▼
                Parameter Validation
                        │
                        ▼
               Statistical Generator
                        │
                        ▼
              Statistical Validation
```

And importantly, this layer can eventually plug into the generation planner we've already built.

# 12. Why M is important for 021

This is where the work starts becoming directly relevant to the actual dataset-generation goal.

A realistic dataset isn't just:

```text

Revenue = random
```

It needs things like:

```text

    → distribution

    → distribution
```

And then later:


# 13. What have we now proven?

I would capture the capability as:

> **FORGE can declaratively generate fields using supported statistical distributions with explicit parameter validation, deterministic seeded behavior, field-order independence, and explicit capability boundaries for unsupported distributions.**

That is a solid architectural capability.

---

# 14. What have we NOT proven yet?

This distinction is important.

020-M proves that individual statistical distributions work.

It does **not** yet prove that:

```text
Distribution A
       +
Distribution B
       +
Constraint
       +
Derived field
```

can all work together.

For example:

```text
CUSTOMER_SCORE ~ NORMAL
        ↓
CREDIT_LIMIT constrained by score
        ↓
ORDER_VALUE ~ LOGNORMAL
        ↓
NET_VALUE = ORDER_VALUE - DISCOUNT
```

That is much harder.

And that's exactly why **020-P and 020-Q** are important.

P introduces statistical relationships between fields.

Q extends that to multi-field statistical relationship graphs.

Then R/R.1/R.2 begin combining statistical behavior with constraints and context-aware generation.
