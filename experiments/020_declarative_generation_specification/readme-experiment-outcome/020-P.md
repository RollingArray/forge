# Experiment 020-P: Declarative Statistical Relationships

## 1. What were we trying to prove?

Suppose we have:

```text
CUSTOMER_SCORE
RISK_SCORE
```

It may be unrealistic to generate them independently.

For example, perhaps:

```text
Higher CUSTOMER_SCORE
        ↓
Lower RISK_SCORE
```

So we may want to specify:

```text
CUSTOMER_SCORE ↔ RISK_SCORE
target correlation = -0.75
```

The experiment tests whether FORGE can turn that declarative requirement into actual generated data exhibiting the requested statistical relationship.

---

# 2. Architecture tested

The experiment uses:

```text
Declarative relationship
        ↓
Parameter validation
        ↓
Correlated latent generation
        ↓
Distribution transformation
        ↓
Correlation validation
```

This is important.

We are not simply generating two random columns and hoping that they happen to correlate.

The relationship itself becomes part of the generation model.

---

# 3. What was tested?

The experiment covers:

### Positive correlation

```text
A ↑
  ↗
B ↑
```

### Negative correlation

```text
A ↑
  ↘
B ↓
```

### Spearman correlation

This checks rank-based relationships rather than only linear Pearson relationships.

It also tests:

* zero correlation
* target sensitivity
* reproducibility
* seed sensitivity
* field-order independence
* invalid target handling
* invalid method handling
* unknown field handling
* no hidden fallback

---

# 4. The actual observed result

The target positive correlation was:

```text
+0.75
```

The generated data achieved:

```text
+0.763
```

The target negative correlation was:

```text
-0.75
```

The generated data achieved:

```text
-0.754
```

Those are quite close to the requested targets.

So the experiment isn't merely saying:

> "Positive correlation works."

It demonstrates that the generator can **target a specified relationship and produce an observed relationship close to it**.

# 6. Why this is a major step beyond M

M gave us:

```text
CUSTOMER_SCORE
    ↓
NORMAL distribution
```

P gives us:

```text
CUSTOMER_SCORE ───────┐
                      │
                 correlation
                      │
                      ▼
                 RISK_SCORE
```

So we have moved from **univariate behavior** to **multivariate behavior**.

That distinction is extremely important for realistic synthetic data.

Real datasets are rarely collections of independent columns.

---

# 7. Why the independent baseline matters

The experiment explicitly includes:

> **Independent generation baseline: PASS**

This gives us a useful control.

We can compare:

```text
Independent generation

A    B
│    │
└────┘
No relationship
```

against:

```text
Correlated generation

A
 \
  → B
```

This gives us evidence that the observed correlation is intentional rather than an accidental artifact of the random generator.

---

# 8. Target sensitivity is particularly valuable

This test passed:

> **Target sensitivity: PASS**

That means changing:

```text
target = +0.25
```

versus:

```text
target = +0.75
```

should materially affect the resulting relationship.

This is important because otherwise the `target_correlation` parameter would effectively be decorative.

The experiment demonstrates that it actually influences generation.

The system correctly distinguishes:

POSITIVE

NEGATIVE

---

# 10. Why "no hidden fallback" matters

Imagine a specification says:

```text
CORRELATION
method = SPEARMAN
target = 0.75
```

but the runtime doesn't support the requested behavior.

A dangerous implementation could silently generate independent values.

The dataset would still look valid at a superficial level.

P explicitly tests against that kind of behavior.

Result:

> **No hidden fallback: PASS**

So an unsupported or invalid relationship cannot silently degrade into unrelated random generation.

---

# 11. Configuration safety passed

The engine rejects:

* invalid target correlations
* invalid methods
* unknown fields

This is important because correlation is mathematically constrained.

For Pearson correlation:

```text
-1 ≤ r ≤ +1
```

A request such as:

```text
r = 1.7
```

must not be accepted.

The experiment confirms that invalid configuration is blocked.

---

# 12. What this means for the FORGE architecture

We now have a much richer statistical model.

Before P:

```text
Field
  ↓
Distribution
  ↓
Value
```

After P:

```text
Field A
    │
    ├── Distribution
    │
    └── Statistical relationship
              │
              ▼
          Field B
              │
              └── Distribution
```

So statistical behavior is no longer just a property of an individual field.

It can also be a property of the **relationship between fields**.

---

# 13. This connects directly to the later Q experiment

P is deliberately limited to a pairwise relationship.

For example:

```text
A ↔ B
```

But real datasets can have:

```text
A ↔ B
B ↔ C
A ↔ C
```

or:

```text
CUSTOMER_SCORE
       ↘
        CREDIT_LIMIT
       ↘
        ORDER_VALUE
```

That is why 020-Q is the natural next experiment.

P proves:

> **Pairwise statistical relationships can be declaratively generated.**

Q asks:

> **Can multiple statistical relationships coexist as a mathematically feasible graph?**

That is a significantly harder problem.

---

# 14. What have we proven?

I would document the capability as:

> **FORGE can declaratively generate statistically related fields by specifying correlation targets and methods, producing observed relationships close to requested targets while preserving direction, reproducibility, seed sensitivity, field-order independence, and explicit configuration safety.**

That's a strong capability statement.

---

# 15. What have we NOT proven?

P does **not** yet prove that arbitrary correlation requirements can coexist.

For example, a specification could request:

```text
A ↔ B = 0.9
B ↔ C = 0.9
A ↔ C = -0.9
```

Those relationships may not form a mathematically valid correlation matrix.

So the engine needs to reason about **joint feasibility**, not merely validate each pair independently.

That's exactly the architectural problem Q addresses.

---

# 16. Why P matters for the eventual real dataset

This is where the experiment becomes directly relevant to your original goal.

Suppose our eventual synthetic dataset contains:

```text
CUSTOMER_SCORE
CREDIT_LIMIT
ORDER_VALUE
RISK_SCORE
RETENTION_SCORE
```

Independent random generation would produce a dataset that may be structurally valid but statistically unrealistic.

With P, we can begin expressing domain hypotheses such as:

```text
CUSTOMER_SCORE
        ↕ +0.75
CREDIT_LIMIT
```

and:

```text
CUSTOMER_SCORE
        ↕ -0.60
RISK_SCORE
```

Now the synthetic dataset starts representing **relationships**, not just values.

That's a major step toward realistic synthetic data.
