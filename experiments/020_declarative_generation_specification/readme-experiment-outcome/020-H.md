# Experiment 020-H: Declarative Relationships and Reference Resolution

## 1. What were we trying to prove?

### In simple terms

020-G established that FORGE understands things like:

> "This is a primary key."

and:

> "This field is a foreign key."

But that alone does not create a usable dataset.

For example:

```text
CUSTOMER
CUS-1
CUS-2
CUS-3
```

and:

```text
ORDER
ORDER-1 → CUS-2
ORDER-2 → CUS-1
ORDER-3 → CUS-2
```

The important question is:

> **Can FORGE actually resolve those references correctly and maintain the relationship between the generated entities?**

020-H tests exactly that.

---

# 2. What did we actually test?

The experiment tested several relationship cardinalities:

```text
1:1
0:1
1:N
0:N
N:M
```

In plain language:

### 1:1

One record corresponds to exactly one record.

```text
CUSTOMER ─── PROFILE
   1          1
```

### 0:1

A relationship is optional.

```text
CUSTOMER ─── PROFILE
   1          0..1
```

Some customers may have no profile.

### 1:N

One parent can have many children.

```text
CUSTOMER
   │
   ├── ORDER
   ├── ORDER
   └── ORDER
```

### 0:N

A parent may have zero or many children.

### N:M

Many records on one side can relate to many records on the other side.

This typically requires an associative entity.

```text
ORDER
  │
  ▼
ORDER_ITEM
  ▲
  │
PRODUCT
```

Everything passed.

**Overall: PASS**

This is a significant result.

---

# 4. What does that actually mean?

In simple terms:

> **FORGE can now generate related entities and resolve references between them while preserving referential integrity.**

This is the point where the output starts becoming a **dataset**, rather than just independently generated tables.

For example:

```text id="1a1k3a"
CUSTOMER
──────────────
CUS-1
CUS-2
CUS-3
```

can become:

```text id="2xqj2v"
ORDER
────────────────
ORD-1 → CUS-2
ORD-2 → CUS-1
ORD-3 → CUS-2
ORD-4 → CUS-3
```

and FORGE verifies that every referenced customer actually exists.

---

# 5. Why referential integrity is important

This is probably the most important test in 020-H.

Suppose an order contains:

```text id="w6skg8"
CUSTOMER_ID = CUS-999
```

but the CUSTOMER table contains only:

```text id="uk3c4w"
CUS-1
CUS-2
CUS-3
```

The dataset is broken.

A synthetic dataset can look perfectly realistic while still being unusable because of broken relationships.

020-H explicitly tests against that.

The result:

> **Referential integrity: PASS**

means FORGE is not simply generating plausible foreign-key-looking strings.

It is resolving references against actual generated identities.

---

# 6. Why the cardinality tests matter

Referential integrity alone isn't enough.

For example, this may technically be referentially valid:

```text id="0x7s0p"
CUSTOMER-1
   ↓
ORDER-1
ORDER-2
ORDER-3
ORDER-4
...
```

But if the specification says:

```text
1:1
```

that would be wrong.

The experiment therefore tests the **shape of the relationship**, not just whether the IDs exist.

This is important because synthetic data needs to reproduce the structural behavior of the source domain.

---

# 7. N:M is particularly important

The experiment also validates:

```text id="x5f3a2a"
N:M associative relationship
```

This is a more complex relational pattern.

Instead of trying to put multiple foreign keys directly into one record, FORGE can represent the relationship through an associative entity.

Conceptually:

```text id="l0t2k5"
CUSTOMER
   │
   │
   ▼
CUSTOMER_PRODUCT
   ▲
   │
   │
PRODUCT
```

or:

```text id="7t4f1h"
ORDER
   │
   ▼
ORDER_ITEM
   ▲
   │
PRODUCT
```

That is an important capability if FORGE is eventually expected to reproduce real enterprise relational structures.

---

# 8. What did we learn?

The major architectural learning is:

> **Identity generation and relationship resolution should be separate capabilities.**

020-G gave us:

```text id="6j9g5w"
Who am I?
```

020-H adds:

```text id="n9b2p6"
Who do I belong to?
```

So:

```text id="4g7q9s"
020-G
Identity
   │
   ▼
020-H
Relationship
   │
   ▼
Referentially valid dataset
```

This is a very clean progression.

---

# 9. Entity-order independence is important here

This experiment also confirms:

```text id="2o4w0v"
Entity-order independence: PASS
```

That's important because relationships inherently introduce dependencies.

We don't want:

```text id="u4f1s9"
Generate CUSTOMER first
   ↓
Works

Generate ORDER first
   ↓
Breaks
```

Instead, FORGE needs to understand the relationship structure and determine an appropriate generation plan.

That is the beginning of **dependency-aware generation**.

---

# 10. What have we now proven?

Together, 020-G and 020-H establish a much stronger capability.

### 020-G

FORGE can generate identities.

### 020-H

FORGE can use those identities to establish relationships.

Therefore:

> **FORGE can declaratively generate relationally connected entities while preserving identity, cardinality, referential integrity, required/optional semantics, and deterministic reference resolution.**

That's a major step toward the actual dataset-generation hypothesis.

---

# 11. What have we NOT proven?

We should still be careful.

020-H does not yet establish:

* complex cross-field constraints
* conditional relationships
* derived fields across entities
* statistical relationships across entities
* dependency cycles
* relationship-aware distributions
* realistic relationship frequencies
* large-scale relational datasets
* conflict detection when relationships and constraints disagree

Those will need separate experiments.
