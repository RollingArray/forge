# Experiment 020-K.1: Constraint Propagation and Feasible Generation

## 1. What were we trying to prove?

### In simple terms

020-K showed that FORGE could represent constraints and detect conflicts, but it could not reliably use those constraints to generate valid values.

So we changed the question.

Instead of asking:

> "Can FORGE generate a value that happens to satisfy a constraint?"

we asked:

> **"Can FORGE propagate the constraints first, calculate the values that are actually possible, and then generate directly inside that feasible region?"**

The intended architecture was:

```text
Specification
      ↓
Constraint extraction
      ↓
Constraint propagation
      ↓
Feasible generation region
      ↓
Direct generation
      ↓
Validation
```

That is a much stronger approach than generate-and-repair.

---

# 2. What did we actually test?

We tested increasingly complex constraint situations.

### Single-field bounds

For example:

```text
CREDIT_LIMIT >= 5000
```

The engine should derive:

```text
CREDIT_LIMIT ∈ [5000, MAX]
```

### Cross-field constraints

For example:

```text
ORDER_VALUE >= MIN_AMOUNT
```

The feasible region for one field depends on another field.

### Chained constraints

For example:

```text
A >= B
B >= C
C >= 100
```

The engine should propagate the implication:

```text
A >= 100
B >= 100
```

without requiring the generator to discover this through trial and error.

We also tested:

* impossible specifications
* field-order independence
* reproducibility
* absence of post-generation repair

# 4. What does this actually tell us?

The important result is that **single-field constraint propagation works**.

FORGE can take something like:

```text
CREDIT_LIMIT >= 5000
```

and use it to restrict generation.

But once constraints depend on other fields, the current propagation model breaks down.

So we have:

```text
Simple:

CREDIT_LIMIT
     │
     ▼
[5000, 10000]
     │
     ▼
Generate
     │
     ▼
Valid
```

working.

But:

```text
Cross-field:

CUSTOMER_SCORE
       │
       ▼
CREDIT_LIMIT
       │
       ▼
Feasible region
```

is not yet working reliably.

---

# 5. Why is the cross-field failure important?

Consider:

```text
CUSTOMER_SCORE = 80
```

and:

```text
CREDIT_LIMIT >= 5000
```

If the specification says the minimum credit limit depends on the score, FORGE needs to calculate the feasible region dynamically.

For example:

```text
CUSTOMER_SCORE = 20
→ CREDIT_LIMIT ∈ [1000, 10000]

CUSTOMER_SCORE = 60
→ CREDIT_LIMIT ∈ [3000, 10000]

CUSTOMER_SCORE = 80
→ CREDIT_LIMIT ∈ [5000, 10000]
```

The generator can't determine `CREDIT_LIMIT` independently.

It needs **context**.

That is the missing architectural capability exposed by K.1.

---

# 6. Chained constraints expose an even deeper issue

Suppose we have:

```text
A >= B
B >= C
C >= 100
```

The generator shouldn't have to figure this out through repeated trial and error.

The constraint graph should propagate:

```text
C >= 100
     ↓
B >= C
     ↓
B >= 100
     ↓
A >= B
     ↓
A >= 100
```

K.1 shows that the current propagation engine does not yet reliably handle this kind of chain.

That is a significant finding.

---

# 7. What DID work?

Three results are particularly valuable.

### Impossible specifications

**PASS**

FORGE can recognize when propagation produces an impossible region.

For example:

```text
X >= 7000
X <= 5000
```

becomes:

```text
[7000, 5000]
```

which is empty.

FORGE blocks it.

### Field-order independence

**PASS**

Constraint propagation does not depend on the order in which fields are declared.

That's important because we already established order-independent semantics in 020-E.1.

### No post-generation repair

**PASS**

This is a particularly good result.

The experiment confirms that the successful constraint handling is based on **direct feasible-region generation**, rather than:

```text
Generate
   ↓
Invalid
   ↓
Repair
   ↓
Try again
```

That is exactly the architectural direction we want.

---

# 8. What did we learn?

The key lesson is:

> **Constraint propagation needs to operate across a dependency graph, not merely at the individual-field level.**

The architecture therefore needs to evolve from:

```text
Constraint
   ↓
Field bounds
   ↓
Generate
```

toward:

```text
Constraint graph
       ↓
Dependency analysis
       ↓
Constraint propagation
       ↓
Context-dependent feasible regions
       ↓
Generation planning
       ↓
Direct generation
```

This is a much more sophisticated generation model.

---

# 10. What have we proven?

For **020-K.1 specifically**, I would say:

> **FORGE can propagate single-field constraints into feasible generation regions and safely reject impossible specifications, while maintaining deterministic, order-independent, repair-free generation. Cross-field and chained constraint propagation remain unresolved.**

That is the honest result.

---

# 11. What have we NOT proven?

We still cannot claim that the constraint engine can generically handle:

* arbitrary cross-field constraints
* multi-level constraint chains
* conditional feasible regions
* constraints combined with statistical distributions
* constraints across entities
* constraints involving derived fields
* large constraint graphs

Those become increasingly important later.

And, importantly, this is exactly why the subsequent **R, R.1, R.2** experiments matter. They eventually test the combination of constraints with statistical generation and record-level feasible regions.

---

# 12. Architectural Outcome

K.1 makes the architectural requirement much clearer:

```text
                Specification
                      │
                      ▼
              Requirement Graph
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
    Dependencies              Constraints
          │                       │
          └───────────┬───────────┘
                      ▼
             Feasibility Analysis
                      │
                      ▼
             Feasible Region
                      │
                      ▼
              Generation Plan
                      │
                      ▼
             Direct Generation
                      │
                      ▼
             Independent Validation
```

The critical addition is **context**.

A field cannot always determine its own feasible region.

Its feasible region may depend on values generated elsewhere.

> **FORGE can perform deterministic, order-independent constraint propagation for single-field bounds and safely reject impossible specifications without post-generation repair. Cross-field and chained constraint propagation remain an architectural gap identified for subsequent experiments.**
