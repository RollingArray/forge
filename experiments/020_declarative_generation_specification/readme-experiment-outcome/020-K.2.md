# Experiment 020-K.2: Constraint-Driven Generation Planning

## 1. What were we trying to prove?

The question was:

> **Can FORGE turn declarative constraints into an explicit generation plan, so that dependent fields are generated in the right order and directly within their feasible regions?**

The architecture tested was:

```text
Specification
      ↓
Constraint extraction
      ↓
Constraint graph
      ↓
Generation planning
      ↓
Context-aware generation
      ↓
Constraint validation
```

This is a meaningful architectural improvement over simply generating values and checking them afterward.

---

## 2. What did we test?

The experiment tested whether FORGE can plan generation for:

### Simple dependencies

For example:

```text
A >= 100
```

Generate `A` inside the valid region.

### Chained dependencies

For example:

```text
A >= B
B >= C
C >= 100
```

The planner must understand:

```text
C
↓
B
↓
A
```

and generate accordingly.

### Strict ordering

If:

```text
A → B
```

then `A` must be resolved before `B`.

### Impossible constraints

For example:

```text
A >= 7000
A <= 5000
```

must block generation.

### Cycles

For example:

```text
A → B
B → C
C → A
```

must also block generation.

And throughout all of this:

* field order must not matter
* the same seed must reproduce the result
* different seeds must produce different valid results
* generation must not rely on post-generation repair

# 4. What does this actually mean?

The important change is that FORGE is no longer thinking about constraints as something that happens **after generation**.

Instead:

```text
Constraint
    ↓
Dependency
    ↓
Generation order
    ↓
Feasible context
    ↓
Generate value
```

For example, consider:

```text
CUSTOMER_SCORE
       ↓
CREDIT_LIMIT
```

where:

```text
CUSTOMER_SCORE = 80
```

might imply:

```text
CREDIT_LIMIT >= 5000
```

FORGE can now conceptually do:

```text
1. Generate CUSTOMER_SCORE
2. Resolve the resulting constraint
3. Calculate feasible CREDIT_LIMIT region
4. Generate CREDIT_LIMIT inside that region
5. Validate independently
```

That's fundamentally different from:

```text
1. Generate both
2. Discover violation
3. Repair
```

# 6. Why "No post-generation repair" matters

This is one of the strongest results in the experiment.

The test passed:

> **No post-generation repair: PASS**

That means the architecture is validating the hypothesis that constraints can influence generation **before the value is produced**.

The desired model is:

```text
        Constraint
             ↓
       Feasibility
             ↓
      Generation Plan
             ↓
       Direct Sample
             ↓
        Validation
```

not:

```text
       Random Sample
             ↓
         Validate
             ↓
        INVALID
             ↓
          Repair
             ↓
       Try again
```

The first is declarative generation.

The second is essentially a repair loop.

---

# 7. Why cycle blocking matters

The planner now has a clear safety boundary.

Consider:

```text
A depends on B
B depends on C
C depends on A
```

There is no valid generation order.

FORGE blocks it.

This is important because once constraints become dependencies, the system is effectively building a directed graph.

Graph safety therefore becomes part of generation correctness.

---

# 8. Why field-order independence matters

The experiment confirms:

```text
Field order ≠ generation semantics
```

For example:

### Specification A

```text
A
B
C
```

and:

### Specification B

```text
C
A
B
```

should produce the same logical generation behavior.

The dependency graph determines the order.

This is a core characteristic of a genuine declarative system.

# 10. What have we proven?

I would document the actual capability as:

> **FORGE can transform declarative constraint dependencies into a deterministic generation plan and use that plan to perform context-aware generation while preserving constraints, dependency ordering, reproducibility, field-order independence, and safety against cycles and impossible specifications, without post-generation repair.**

That is a meaningful capability statement.

---

# 11. What have we NOT proven yet?

We should still avoid overclaiming.

K.2 does **not** prove that arbitrary real-world constraints can be handled.

We have not yet established generic support for:

* complex nonlinear constraints
* large constraint graphs
* statistical constraints
* cross-entity constraints
* constraints combined with derived fields
* constraints combined with conditional rules
* constraints combined with distributions
* record-level feasible regions at scale

Those are exactly the harder questions addressed later in 020.

And this is why **020-R.2 is particularly significant**. It eventually demonstrates constraint-conditioned statistical generation at the record level with **18/18 PASS**.
