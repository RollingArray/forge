## Experiment 020-B: Generic Generation

### 1. What were we trying to prove?

**In simple terms**

In 020-A, we proved that FORGE could understand a specification.

Now we asked a more important question:

> **Can the same specification actually be executed to generate data without writing dataset-specific generation code?**

In other words, we moved from:

```text
"Can FORGE understand the blueprint?"
```

to:

```text
"Can FORGE actually build something from the blueprint?"
```

---

### 2. What did we do?

We took the same versioned specification from 020-A and attempted to generate **10 records per entity**.

The experiment exposed executable capabilities for:

**Types**

```text
BOOLEAN
CATEGORICAL
CODE
CURRENCY
DATE
DATETIME
DECIMAL
ENUM
FLOAT
IDENTIFIER
INTEGER
PERCENTAGE
STRING
TIME
```

**Generation strategies**

```text
CONSTANT
NULL
RANDOM
SEQUENTIAL
```

**Distributions**

```text
CATEGORICAL
DISCRETE_UNIFORM
NORMAL
UNIFORM
```

The important architectural test was that the generator should execute the specification generically.

---

### 3. What happened?

The specification itself continued to validate successfully:

```text
Specification structure          PASS
Controlled vocabulary             PASS
Entities and fields               PASS
Relationships                     PASS
Rules                             PASS
Statistical behavior              PASS
Scenarios                         PASS
Validation configuration          PASS
Provenance configuration          PASS
Reproducibility configuration     PASS
```

But execution stopped with:

```text
ERROR:
Strategy 'TRANSFORM' is registered
but not executable in 020-B.
```

**Overall: FAIL**

---

## 4. What does that actually mean?

This is a very important distinction.

FORGE had been told:

> "`TRANSFORM` is a valid generation strategy."

The specification therefore accepted it.

But when FORGE actually tried to use it, the generation engine said:

> "I know about this strategy, but I don't actually know how to execute it yet."

So we discovered a gap between:

```text
REGISTERED CAPABILITY
        ≠
EXECUTABLE CAPABILITY
```

That is valuable architectural evidence.

---

## 5. Why is this failure important?

Because it exposed a potentially dangerous design problem.

Imagine we had allowed the experiment to continue and silently substitute another strategy.

We could have ended up with:

```text
Specification
     │
     ▼
TRANSFORM
     │
     X
     │
     ▼
Random fallback
     │
     ▼
Generated data
```

The dataset might look valid while actually violating the user's specification.

That would be much worse than failing.

020-B therefore reinforces an important FORGE principle:

> **A declared capability must not be treated as executable unless the engine can actually execute it.**

And if it cannot execute it, FORGE should fail explicitly.

---

## 6. What did we learn?

The first generic-generation experiment exposed the need for a **capability boundary**.

We need to distinguish at least three states:

```text
DECLARED
    │
    ▼
SUPPORTED / VALIDATED
    │
    ▼
EXECUTABLE
```

A capability being present in the vocabulary does not automatically mean that the generator supports it.

This becomes especially important as FORGE grows.

---

## 7. What did we NOT prove?

Because execution stopped at the capability boundary, 020-B does **not** establish that:

* FORGE can successfully generate the complete dataset.
* All supported types work during generation.
* All executable strategies work correctly.
* Distributions produce the expected behavior.
* Generated records satisfy relationships.
* Generated records satisfy constraints.
* Generation is reproducible end-to-end.

Those questions remain open.

---

## 8. Architectural outcome

### Before 020-B

We had:

```text
Controlled vocabulary
        ↓
"TRANSFORM" is a valid strategy
```

### After 020-B

We learned that the architecture must explicitly distinguish:

```text
                  Capability
                     │
             ┌───────┴───────┐
             ▼               ▼
        Registered        Executable
             │               │
             │               ▼
             │          Generation
             │
             └── not enough ──►
```

This capability boundary later becomes important in **020-M, 020-N, 020-S**, and the other experiments where we explicitly test deferred or unsupported capabilities.

---

## 9. Resulting FORGE capability

**Not yet a PASS.**

The experiment established:

> **FORGE can detect when a generation strategy is declared in the specification but is not actually executable, and it refuses to silently continue.**

That is a **safety capability**, not yet a generation capability.

---

### Architectural significance

**Category:** Capability-boundary discovery

**Status:** **FAIL, intentionally informative**

The important thing is that **we should preserve this failure in the final 020 story**.

It tells a much better engineering story than pretending 020-B was always green:

> 020-A established the contract.
> 020-B attempted to execute it and exposed a mismatch between declared and executable capabilities.
> Subsequent architecture then needed to make capability assessment explicit.
