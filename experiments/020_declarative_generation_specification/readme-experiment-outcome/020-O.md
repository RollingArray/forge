# Experiment 020-O: Declarative Scenario Generation

## 1. What were we trying to prove?

In simple terms:

> **Can FORGE generate different realistic dataset conditions from the same base specification by applying declarative scenario parameters, overrides, distributions, and constraints?**

For example, imagine the same customer/order model being used for:

```text id="9r4x2k"
NORMAL
        ↓
Typical business population

PREMIUM_HEAVY
        ↓
Much larger premium-customer population

STRESS
        ↓
High-volume / extreme operating conditions
```

We don't want three separate specifications.

We want:

```text id="3k7p1m"
Base Specification
        +
Scenario
        ↓
Generated Dataset
```

That is a much more scalable model.

---

# 2. Architecture tested

The experiment uses:

```text id="9q5m2v"
Base Specification
       ↓
Scenario Parameters
       ↓
Scenario Overrides
       ↓

       ↓

```

This is important because the scenario is not simply a random "mode."

It can affect multiple aspects of generation.

# 5. The most important result

I would highlight:

> **Base specification immutability: PASS**

This means applying a scenario does not mutate the underlying specification.

Conceptually:

```text id="x8p3q6"
                     Base Specification
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
           NORMAL     PREMIUM_HEAVY    STRESS
              │            │            │
              ▼            ▼            ▼
          Dataset A     Dataset B     Dataset C
```

The base remains unchanged.

That is important because otherwise running one scenario could contaminate another scenario.

---

# 6. Scenario isolation passed

This test is closely related.

If we generate:

```text id="7q3m9p"
NORMAL
```

and then:

```text id="6v1x4k"
PREMIUM_HEAVY
```

the second run should not inherit modified state from the first.

The result:

> **Scenario isolation: PASS**

confirms that scenario execution behaves like an isolated configuration layer.

---

# 7. Distribution overrides passed

This is a particularly useful capability.

A scenario can change statistical behavior without rewriting the field definition.

For example:

```text id="p8w4m2"
Base:
CUSTOMER_TYPE
  STANDARD = 70%
  PREMIUM  = 20%
  SPECIAL  = 10%
```

A scenario could override it:

```text id="m5x7q1"
PREMIUM_HEAVY:
  PREMIUM = 60%
```

The underlying field remains the same.

The scenario changes the generation behavior.

This is exactly the kind of abstraction that becomes useful for test-data generation.

---

# 8. Scenario constraints passed

The STRESS scenario demonstrates this nicely:

```text id="v6q2n9"
ORDER_COUNT >= 3000
```

The result shows:

```text id="q3m8p1"
Orders >= 3000: 100.00%
```

So scenarios can impose behavioral conditions rather than merely changing parameters.

That means we can eventually express things like:

```text id="6r2k7m"
NORMAL
    → normal customer mix

PEAK_SEASON
    → higher order volume

SUPPLY_DISRUPTION
    → delayed shipments

PREMIUM_HEAVY
    → higher premium population

FAILURE_MODE
    → controlled invalid / exceptional conditions
```

This starts to make FORGE useful for **scenario-based testing**, not just synthetic data generation.

# 9. Why scenario parameter behavior matters

The experiment also confirms:

> **Scenario parameter behavior: PASS**

This means parameters can influence generation without requiring hard-coded logic for every scenario.

Conceptually:

```text id="s7n2p4"
Scenario Parameter
       ↓
Resolution
       ↓
Generation behavior
```

rather than:

```text id="c8m5q1"
if scenario == "PREMIUM_HEAVY":
    do_special_thing()
```

That distinction matters architecturally.

We want scenarios to remain declarative.

---

# 10. Invalid scenario blocking is important

The system also correctly rejects invalid scenarios.

That means we have:

```text id="k9p4x2"
Scenario requested
      ↓
Validate
      ↓
Valid? ── NO ──> BLOCK
      │
     YES
      ↓
Generate
```

The same applies to invalid distributions.

Again, the system does not silently guess.

# 12. Why O matters for the eventual real dataset

This is where O becomes much more than a feature experiment.

When we eventually generate the first meaningful dataset in 021, we shouldn't generate just one dataset.

We should be able to say:

```text id="5q8n3m"

    NORMAL
    PREMIUM_HEAVY
    STRESS
```

and get three controlled populations from the same declarative model.

That gives us a way to test whether the generated data behaves appropriately under different business conditions.

# 14. What have we actually proven?

I would document the capability as:

> **FORGE can generate isolated dataset variants from a shared declarative specification by applying scenario-specific parameters, overrides, distributions, and constraints while preserving specification immutability, deterministic behavior, configuration safety, and independence from entity or field declaration order.**

That's a meaningful capability.

---

# 15. What have we NOT proven yet?

We have proven scenario behavior in a controlled environment.

We have **not yet proven** that scenarios can safely modify the behavior of the full integrated generation engine.

For example, we haven't yet demonstrated the complete chain:

```text id="5n8q2r"
PREMIUM_HEAVY
      ↓
customer distribution changes
      ↓
customer scores change
      ↓
credit limits change
      ↓
order values change
      ↓
statistical relationships remain valid
      ↓
constraints remain valid
      ↓
derived values remain valid
      ↓
shipments remain consistent
```

That is a much stronger test.

And that distinction becomes important when we decide whether 020 is actually ready to close.

## Where O fits in the bigger 020 story

At this point, the architecture is becoming quite compelling:

```text id="4v8m2q"
                    Base Specification
                           │
                           ▼
                    Scenario Selection
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
       NORMAL        PREMIUM_HEAVY        STRESS
          │                │                │
          └────────────────┼────────────────┘
                           ▼
                 Declarative Generation
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
      Statistics       Constraints      Relationships
          │                │                │
          └────────────────┼────────────────┘
                           ▼
                    Context Resolution
                           │
                           ▼
                    Derived / Conditional
                           │
                           ▼
                       Validation
```

And I think O gives us an important conceptual distinction for the final FORGE product:

> **The specification defines what the data model is. The scenario defines what world we want that model to represent.**

That is a very useful abstraction.

For 021, this means we can stop thinking about "generate 10,000 random records" and instead think about **generating a controlled synthetic world under a declared business scenario**.
