# Experiment 020-B.1: Runtime Capability Assessment

## 1. What were we trying to prove?

### In simple terms

020-B taught us something important.

FORGE's specification can say:

> "I want to use `TRANSFORM`, `REFERENCE`, `DERIVED`, `BETA`, `GAMMA`, etc."

But the runtime may not know how to execute all of those capabilities yet.

So instead of letting generation fail halfway through, we asked:

> **Can FORGE look at the specification first, determine exactly what it can and cannot execute, and create a generation plan before attempting to generate data?**

This is the difference between:

```text
Try to generate
     ↓
Discover something isn't supported
     ↓
Crash
```

and:

```text
Understand specification
     ↓
Check capabilities
     ↓
Build execution plan
     ↓
Tell us what can/cannot run
     ↓
Generate only if safe
```

---

## 2. What did we actually do?

We took the same declarative specification and assessed **every field individually** against the capabilities currently implemented in the runtime.

The specification contained **47 fields** across the entities.

For every field, FORGE checked:

1. Is the field type executable?
2. Is the generation strategy executable?
3. Is the requested distribution executable?
4. Can the field therefore be executed by the current runtime?

The runtime currently supports:

### Executable types

All 14 declared types were executable.

### Executable strategies

```text
CONSTANT
NULL
RANDOM
SEQUENTIAL
```

### Executable distributions

```text
CATEGORICAL
DISCRETE_UNIFORM
NORMAL
UNIFORM
```

Other capabilities remained valid vocabulary but were deferred.

---

## 3. What happened?

This time, FORGE **did not attempt generation**.

It assessed all 47 fields:

```text
Fields assessed:  47
Executable:       20
Deferred:         27
Plan status:      BLOCKED
```

And the overall experiment **PASSED**.

The important part is:

```text
Specification validity: PASS
Capability assessment:  PASS
Generation:            BLOCKED
Overall:               PASS
```

The generation was deliberately blocked because the specification contained valid FORGE capabilities that the current runtime could not yet execute.

---

# 4. What does that actually mean?

Think of it like ordering a meal from a menu.

The FORGE specification is the **menu order**:

```text
I want:
  TRANSFORM
  REFERENCE
  DERIVED
  BETA
  GAMMA
  ...
```

The runtime is the **kitchen**.

The menu can contain dishes that the restaurant intends to offer eventually, but the kitchen may not be equipped to prepare every dish today.

020-B effectively discovered this by trying to cook.

020-B.1 changes the behavior.

Now FORGE checks the kitchen **before cooking**.

```text
Specification
      ↓
"Can I make everything requested?"
      ↓
      NO
      ↓
Generation BLOCKED
      ↓
Execution plan explains why
```

That is much safer.

---

# 5. What did the execution plan tell us?

The experiment produced a field-level assessment.

For example:

```text
CUSTOMER
  CUSTOMER_ID
      EXECUTABLE

  CUSTOMER_CODE
      DEFERRED
      Reason: strategy 'TRANSFORM' is not executable

  CUSTOMER_SCORE
      DEFERRED
      Reason: distribution 'BETA' is not executable
```

And:

```text
ORDER
  CUSTOMER_ID
      DEFERRED
      Reason: strategy 'REFERENCE' is not executable

  SUBTOTAL
      DEFERRED
      Reason: strategy 'DERIVED' is not executable

  NET_AMOUNT
      DEFERRED
      Reason: strategy 'FORMULA' is not executable
```

This is significantly better than a generic error such as:

```text
Unsupported strategy.
```

FORGE can now tell us **exactly which parts of the specification are executable and which are not**.

---

# 6. Why is this important?

This experiment establishes a very important architectural boundary:

> **Vocabulary support is not the same thing as runtime capability.**

We now have three distinct concepts:

```text
                    FORGE Capability
                          │
             ┌────────────┼────────────┐
             ▼            ▼            ▼
          Declared     Assessed     Executable
          vocabulary   capability    capability
```

A capability can therefore be:

```text
VALID FORGE VOCABULARY
        │
        ▼
RUNTIME ASSES IT
        │
   ┌────┴────┐
   ▼         ▼
EXECUTABLE  DEFERRED
```

That is a much stronger architecture than assuming that everything in the vocabulary is immediately executable.

---

# 7. What did we learn from 020-B → 020-B.1?

This is one of the first examples where the **failure of one experiment directly shaped the next architectural move**.

### 020-B

We tried to generate immediately.

Result:

```text
FAIL

TRANSFORM is registered
but not executable.
```

### Architectural problem discovered

FORGE was not distinguishing clearly enough between:

```text
"valid capability"
```

and:

```text
"currently executable capability"
```

### 020-B.1

We introduced capability assessment **before generation**.

Result:

```text
47 fields assessed
20 executable
27 deferred
Generation safely blocked
Overall PASS
```

### Architectural improvement

```text
Before:

Specification
     ↓
Generation
     ↓
Failure


After:

Specification
     ↓
Capability Assessment
     ↓
Execution Plan
     ↓
Generation
```

This is exactly the kind of architectural evolution we want the 020 document to capture.

---

# 8. What have we NOT proven yet?

020-B.1 still does **not** prove that FORGE can successfully generate the full dataset.

In fact, it explicitly proves the opposite for this particular specification:

> The current runtime cannot execute all 47 requested fields.

We have not yet proven:

* that the 20 executable fields generate correctly together
* that deferred capabilities can eventually be implemented cleanly
* that dependencies between executable and deferred fields are handled correctly
* that generated values satisfy relationships
* that generated values satisfy constraints
* that statistical behavior is correct
* that the final dataset is useful

Those are intentionally left for subsequent experiments.

---

# 9. Architectural Outcome

### Before 020-B

The runtime effectively had:

```text
Specification
     ↓
Try generation
```

### After 020-B.1

We now have:

```text
Specification
     ↓
Capability Assessment
     ↓
Execution Plan
     ↓
Generation Decision
     │
     ├── SAFE → Generate
     │
     └── BLOCKED → Explain what is missing
```

This is a major architectural improvement because **generation is now gated by capability awareness**.

---

# 10. Resulting FORGE Capability

> **FORGE can inspect a declarative specification before generation, determine which requested capabilities are executable, identify deferred capabilities at field level, produce an execution plan, and safely block generation when the specification cannot be fully executed.**

That is a real product capability.
