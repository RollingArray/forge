# Experiment 020-I: Declarative Dependency Graph and Generation Planning

## 1. What were we trying to prove?

### In simple terms

020-H established that FORGE can generate related entities.

But once relationships become more complicated, FORGE cannot simply generate entities in whatever order they appear in the specification.

For example:

```text
CUSTOMER
   │
   ▼
ORDER
   │
   ▼
ORDER_ITEM
   │
   ▼
SHIPMENT
```

Before generating `ORDER`, FORGE needs the relevant `CUSTOMER` identities.

Before generating `ORDER_ITEM`, it needs the `ORDER` and `PRODUCT` identities.

Before generating `SHIPMENT`, it needs the `ORDER` identity.

So the question was:

> **Can FORGE look at the declarative relationships, build a dependency graph, detect unsafe configurations, and determine a valid generation order automatically?**

---

# 2. What did we actually do?

The experiment represents dependencies as:

```text
parent → child
```

meaning:

> The parent must be generated before the child.

For example:

```text
CUSTOMER → ORDER
```

means:

```text
Generate CUSTOMER first
        ↓
Generate ORDER
```

We then tested the dependency planner against:

* simple dependencies
* transitive dependencies
* multiple dependencies
* independent entities
* associative entities
* optional dependencies
* disconnected components
* self-references
* dependency cycles
* unknown entities
* invalid cardinalities

And importantly:

> The planner was tested independently of the order in which entities were declared.

# 4. What does that actually mean?

The important outcome is:

> **FORGE can derive a generation plan from the relationships rather than relying on the order in which entities happen to appear in the specification.**

For example, suppose the specification happens to list:

```text id="n1u7a8"
SHIPMENT
PRODUCT
ORDER_ITEM
CUSTOMER
ORDER
```

That doesn't mean FORGE should try to generate them in that order.

The dependency graph can determine:

```text id="m1o7a8"
CUSTOMER
    ↓
ORDER
    ↓
ORDER_ITEM
    ↓
SHIPMENT

PRODUCT
    ↓
ORDER_ITEM
```

and derive a valid execution plan.

---

# 5. Why is this important?

This is the point where **declarative specification starts becoming genuinely declarative**.

Without dependency planning, the specification would secretly mean:

> "Generate these things in the order I wrote them."

With dependency planning, it means:

> "Here are the entities and their relationships. You figure out how they need to be generated."

That is a major architectural difference.

```text id="y0g9b5"
Imperative approach:

Step 1 → CUSTOMER
Step 2 → ORDER
Step 3 → ORDER_ITEM
Step 4 → SHIPMENT
```

versus:

```text id="9kmx5u"
Declarative approach:

CUSTOMER → ORDER → ORDER_ITEM → SHIPMENT
       \                 ↑
        └── PRODUCT ─────┘

        ↓

FORGE derives execution order
```

---

# 6. Transitive dependencies are especially important

Consider:

```text id="o9r5sh"
CUSTOMER
   ↓
ORDER
   ↓
ORDER_ITEM
   ↓
SHIPMENT
```

`SHIPMENT` doesn't directly depend on `CUSTOMER`.

But it indirectly depends on it:

```text id="h1l1bb"
SHIPMENT
   ↓
ORDER_ITEM
   ↓
ORDER
   ↓
CUSTOMER
```

FORGE needs to understand that chain.

The experiment confirms:

> **Transitive dependency planning works.**

That becomes critical as the specification grows.

---

# 7. Multiple dependencies also passed

A realistic entity can depend on more than one parent.

For example:

```text id="0ak6xy"
ORDER_ITEM
     │
     ├──── ORDER
     │
     └──── PRODUCT
```

So FORGE cannot simply create one linear chain.

It needs to understand a graph:

```text id="91m5w2"
CUSTOMER ──→ ORDER ──→ ORDER_ITEM
                         ↑
PRODUCT ─────────────────┘
```

The planner handles this.

That is a much more realistic representation of enterprise relational data.

---

# 8. Cycle detection is a critical safety feature

The experiment also proves that FORGE detects dependency cycles.

For example:

```text id="h5o7vq"
A → B
B → C
C → A
```

There is no valid starting point.

A naive generator might:

```text
Generate A
  ↓
needs B
  ↓
needs C
  ↓
needs A
  ↓
loop forever
```

FORGE instead detects the cycle and blocks the configuration.

That is a very important safety property.

---

# 9. Self-reference safety

The experiment also tested:

```text id="br8z5n"
EMPLOYEE
   │
   └── MANAGER_ID → EMPLOYEE_ID
```

Self-referencing structures are common in enterprise data.

They cannot simply be treated like ordinary parent-child relationships because the same entity participates on both sides.

The experiment confirms that FORGE handles the configuration safely rather than blindly producing an invalid plan.

---

# 10. Entity-order independence is now becoming a core property

We've now seen this property appear repeatedly:

```text id="9a8g7f"
020-E.1   Field-order independence
020-F     Field-order independence
020-G     Field-order independence
020-H     Entity-order independence
020-I     Entity-order independence
```

This isn't accidental anymore.

It is becoming an explicit FORGE architectural principle:

> **Declaration order should not determine execution semantics unless the specification explicitly declares a dependency.**

That is exactly what we want from a declarative system.

---

# 11. What did we learn?

The central learning is:

> **Relationships need to be converted into a dependency graph before generation begins.**

The architecture is therefore becoming:

```text id="z1l6k2"
Declarative Specification
          │
          ▼
   Relationship Analysis
          │
          ▼
   Dependency Graph
          │
          ▼
   Cycle / Safety Check
          │
          ▼
 Topological Generation Plan
          │
          ▼
      Generation
```

This is a significant architectural component.

---

# 12. What have we now proven?

Together, 020-G, 020-H, and 020-I establish a strong chain:

### 020-G

> FORGE understands identity.

### 020-H

> FORGE can resolve relationships between identities.

### 020-I

> FORGE can derive a safe generation order from those relationships.

Therefore:

> **FORGE can transform declarative entity relationships into a deterministic, dependency-aware generation plan while detecting cycles and invalid configurations.**

That is a real architectural capability.

---

# 13. What have we NOT proven?

We still have not proven that the **entire dependency graph can drive generation of all dependent fields correctly**.

For example:

```text id="bq0x0p"
CUSTOMER
   ↓
ORDER
   ↓
ORDER_VALUE
   ↓
DISCOUNT
   ↓
NET_AMOUNT
```

Here we are no longer dealing only with entity dependencies.

We now have:

* entity dependencies
* field dependencies
* derived values
* conditional rules
* cross-field constraints
* statistical relationships

That is the next level of complexity.

020-I establishes the graph foundation, but not the complete joint-generation engine.

---

# 14. Architectural Outcome

The FORGE architecture now has a clear planning layer:

```text id="v1j8lq"
                  Specification
                       │
                       ▼
              Requirement Extraction
                       │
                       ▼
              Dependency Graph
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
       Safety Analysis      Dependency Analysis
             │                   │
             └─────────┬─────────┘
                       ▼
              Generation Plan
                       │
                       ▼
                  Generation
```

This is important because **generation should no longer be responsible for figuring out dependencies while it is already generating data**.

The planning problem is solved first.

Then generation executes the plan.
