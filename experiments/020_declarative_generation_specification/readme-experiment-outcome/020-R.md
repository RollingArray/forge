# Experiment 020-R: Declarative Constraint and Statistical Integration

## 1. What were we trying to prove?

We had independently established:

* constraints can drive generation through K.2
* derived and conditional generation works through L
* statistical generation works through M
* pairwise statistical relationships work through P
* multi-field statistical graphs work through Q

R asks:

> **Can these capabilities be combined into one coherent generation process?**

The intended architecture is:

```text
Declarative specification
        ↓
Statistical relationships
        ↓
Constraint analysis
        ↓
Dependency planning
        ↓
Context-aware generation
        ↓
Derived / conditional generation
        ↓
Unified validation
```

This is the first real **joint-generation test**.

The integrated specification contains:

```text
Statistical relationships: 2

Conditional rules:         1

```

So this is no longer testing one capability at a time.

It is testing interactions between them.

# 5. What this tells us

This is very similar to what we saw in N, but R isolates it more precisely.

N asked:

> Can the whole complex declarative system work together?

N failed.

N.1 isolated one piece:

> Can cross-entity context resolution work?

N.1 passed 12/12.

R now asks:

> Can **statistics + constraints + conditional + derived generation** work together?

R fails.

That is a much more useful diagnosis.

# 6. The architectural gap is becoming clear

We currently have strong individual capabilities:

```text id="2m7v9q"
                 FORGE
                   │
      ┌────────────┼────────────┐
      ▼            ▼            ▼
 Constraints    Statistics    Expressions
      │            │            │
      ▼            ▼            ▼
   K.2 PASS      Q PASS       L PASS
```

But when combined:

```text id="3n8q5m"
Constraints
     +
Statistics
     +
Expressions
     +
Conditional logic
        ↓
      R
        ↓
     FAIL
```

This strongly suggests that the problem isn't the individual engines.

It is their **composition contract**.

# 7. Why dependency planning passing is important

R says:

```text
Dependency planning: PASS
```

That means the system understands something like:

```text id="q7m3v1"
SOURCE
  ↓
STATISTICAL VALUE
  ↓
CONSTRAINT
  ↓
DERIVED VALUE
  ↓
CONDITIONAL VALUE
```

But understanding the order is not enough.

The runtime also needs to know:

> What information does each generation mechanism consume and produce?

For example:

```text id="7n2p5q"
Statistical generator
    INPUT:
      distribution
      relationship context
      constraint context

    OUTPUT:
      generated value
      statistical state
```

while:

```text id="0w4m8k"
Constraint engine
    INPUT:
      current context

    OUTPUT:
      feasible region
```

and:

```text id="5r8q2m"
Derived engine
    INPUT:
      resolved dependencies

    OUTPUT:
      deterministic value
```

Those contracts need to fit together.

---

# 8. Why reproducibility fails

This is one of the biggest clues:

> **Reproducibility: FAIL**

We have already proven reproducibility separately in:

* E.1
* L
* M
* P
* Q

So why does it fail when combined?

Because multiple generators are now interacting with shared execution state.

The architecture must guarantee something like:

```text id="v8m3q1"
MASTER SEED
    │
    ├── CUSTOMER_SCORE stream
    ├── RISK_SCORE stream
    ├── CREDIT_LIMIT stream
    ├── DISCOUNT stream
    └── ...
```

The stream assigned to a field should not change merely because another capability happens to execute before it.

This is exactly where the earlier **field-stream isolation work from E.1** needs to become a first-class part of the unified execution model.

---

# 9. Why field-order independence fails

This is another strong clue.

We already proved:

```text id="2m5q7v"
Field-order independence
        PASS
```

in many isolated experiments.

But R reports:

```text id="k8p3m1"
Field-order independence
        FAIL
```

That tells us that the combined execution path is probably still allowing execution order to leak into behavior.

In a truly declarative system:

```text id="0z6q4m"
Specification order
        ≠
Execution order
```

The dependency graph should determine execution.

R demonstrates that this principle hasn't yet been enforced across every capability.

---

# 10. Why constraints and statistics are difficult together

This is the fundamental problem R is exposing.

Suppose:

```text id="q8m3p7"
CUSTOMER_SCORE ~ Normal(70, 10)
```

and:

```text id="f6r2n9"
CREDIT_LIMIT >= CUSTOMER_SCORE × 100
```

Statistical generation wants to generate according to a distribution.

Constraint generation wants to restrict the feasible region.

Those are not independent operations.

You cannot simply:

```text id="9k4m2p"
1. Generate from distribution
2. Check constraint
```

because that can violate the **no post-generation repair** principle.

You need:

```text id="5x7q1m"
Distribution
      +
Constraint
      ↓
Conditional / truncated feasible distribution
      ↓
Generate
```

That is a fundamentally different generation operation.

And this is exactly why R.1 and R.2 become important.

---

# 11. Why conditional and derived fields fail

Consider:

```text id="7m2q9p"
CUSTOMER_SCORE
       ↓
CREDIT_LIMIT
       ↓
ORDER_VALUE
       ↓
DISCOUNT
       ↓
NET_ORDER_VALUE
```

Now imagine `ORDER_VALUE` also has a statistical relationship with another field.

The generator must understand:

```text id="8p4m6q"
ORDER_VALUE
    │
    ├── constrained
    ├── statistically related
    ├── dependency source
    └── input to derived field
```

A field is no longer simply:

```text
"generate me a number"
```

It becomes a **node participating in multiple semantic contracts**.

That is the core problem R exposes.

---

# 12. This is actually a very valuable failure

I would strongly resist simply saying:

> "R failed, so let's fix R."

The better interpretation is:

> **R demonstrates that FORGE needs a unified joint-generation abstraction where statistical behavior and feasibility constraints are solved together before sampling.**

That is a genuine architectural discovery.

---

# 13. The next architectural move

This is exactly why **020-R.1** exists.

R.1 should introduce:

```text id="0m7q3p"
Specification
      ↓
Requirement extraction
      ↓
Unified feasibility analysis
      ↓
Joint generation planning
      ↓
Direct generation
      ↓
Independent validation
```

The key new concept is:

### Unified feasibility

Instead of:

```text id="2q5m8v"
Statistics → generate
Constraints → validate
```

we need:

```text id="9r3k7p"
Statistics
    +
Constraints
    ↓
Unified feasible generation region
    ↓
Generate directly
```

That is the right architectural response to R.

---

# 14. What R has proven

I would document the result as:

> **The first integrated attempt to combine statistical relationships, constraints, conditional rules, and derived fields exposes a composition gap. Although dependency planning, impossible-specification detection, and capability boundaries remain reliable, the current runtime cannot yet preserve statistical behavior, constraints, deterministic execution, and field-order independence when these capabilities participate in the same generation flow.**

That's honest and technically useful.

---

# 15. What R has NOT proven

It does **not** mean:

> Statistical relationships don't work.

Q proved they do.

It does **not** mean:

> Constraints don't work.

K.2 proved they do.

It does **not** mean:

> Derived fields don't work.

L proved they do.

Instead:

> **Their joint execution model is incomplete.**

That's the important distinction.
