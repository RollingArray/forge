# Experiment 020-Q: Declarative Multi-Field Statistical Relationships

## 1. What were we trying to prove?

The question was:

> **Can FORGE take multiple declarative statistical relationships, determine whether they can coexist mathematically, generate the fields together, and verify that the requested relationships were actually achieved?**

This is substantially harder than P.

P dealt with:

```text
A ↔ B
```

Q deals with a graph:

```text
A ↔ B
B ↔ C
A ↔ C
...
```

The architecture tested was:

```text
Declarative relationships
        ↓
Correlation graph
        ↓
Correlation matrix
        ↓
Feasibility analysis
        ↓
Multivariate generation
        ↓
Achieved relationship validation
```

---

# 2. The actual correlation graph

The experiment generated this matrix:

```text
                    CREDIT     CUSTOMER    RETENTION    RISK

CUSTOMER_SCORE      0.750      1.000       0.000       -0.600
RETENTION_SCORE     0.000      0.000       1.000        0.000
RISK_SCORE          0.000     -0.600       0.000        1.000
```

So the specification effectively says:

```text
CREDIT_LIMIT
      ↕ +0.75
CUSTOMER_SCORE
      ↕ -0.60
RISK_SCORE

RETENTION_SCORE
      ↕ 0
everything else
```

This is already beginning to look like a real data model rather than independent random columns.

---

# 3. Why the correlation matrix matters

This is one of the most important architectural results.

You cannot simply validate each requested relationship independently.

For example:

```text
A ↔ B = +0.9
B ↔ C = +0.9
A ↔ C = -0.9
```

might look like three individually valid requests.

But together they may not represent a mathematically valid correlation structure.

Therefore FORGE needs to reason about the **whole system**.

Q explicitly does that:

```text
Relationships
      ↓
Correlation Matrix
      ↓
Feasibility Analysis
```

And the experiment reports:

> **Positive semidefinite: PASS**

That means the requested correlation structure passed the mathematical feasibility check.

# 5. The most important result

I would highlight:

> **Positive-semidefinite validation: PASS**

This means FORGE isn't simply accepting a collection of correlation requests.

It first asks:

> "Can these relationships mathematically coexist?"

That is an important safety boundary.

The architecture is therefore:

```text id="f6k2s8"
Declarative requirements
        ↓
Mathematical feasibility
        ↓
If feasible → generate
If infeasible → block
```

This is much stronger than:

```text

↓

```

# 6. Impossible graph blocking is equally important

The experiment deliberately includes an impossible relationship graph.

The result:

> **Impossible graph blocking: PASS**

This confirms that FORGE refuses to generate a dataset from an incoherent statistical specification.

That's a critical property for an engineering-grade synthetic data system.

The system should never silently relax:

```text
Requested correlation = 0.9
```

into:

```text
Observed correlation = 0.3
```

and claim success.

# 7. Three-field generation passed

This is where Q moves beyond mathematical validation.

It actually generates multiple statistically related fields together.

For example:

```text id="7v2m9p"
CUSTOMER_SCORE
       │
       ├── +0.75 → CREDIT_LIMIT
       │
       └── -0.60 → RISK_SCORE
```

The generator must produce the fields jointly rather than generating them independently.

Result:

> **Three-field generation: PASS**

That is a meaningful execution result.

# 8. Shared-source relationships passed

This is particularly important.

One source field can participate in multiple relationships:

```text id="n8q3w7"
             CREDIT_LIMIT
                  ▲
                  │ +0.75
                  │
CUSTOMER_SCORE ───┤
                  │ -0.60
                  ▼
              RISK_SCORE
```

So `CUSTOMER_SCORE` isn't simply part of one pair.

It is a node in a statistical graph.

The experiment confirms:

> **Shared-source relationships: PASS**

That means the relationship model can handle graph topology rather than only isolated pairs.

# 10. Why field-order independence matters here

A statistical graph should not depend on the order in which fields appear in the specification.

For example:

```text id="5w7k3m"
CUSTOMER_SCORE
CREDIT_LIMIT
RISK_SCORE
```

and:

```text id="9p2q6v"
RISK_SCORE
CUSTOMER_SCORE
CREDIT_LIMIT
```

must describe the same statistical system.

Result:

> **Field-order independence: PASS**

This reinforces the declarative nature of the model.

---

# 11. Duplicate conflict blocking

This is a subtle but valuable safety test.

Suppose the specification says:

```text id="v2p7m4"
A ↔ B = +0.7
A ↔ B = -0.5
```

Those are conflicting declarations.

FORGE must not silently pick one.

The experiment confirms:

> **Duplicate conflict blocking: PASS**

Again, explicit failure is preferable to silent interpretation.

---

# 12. Zero relationships are meaningful

The experiment also tests:

> **Zero relationship: PASS**

This is useful because:

```text
correlation = 0
```

is not the same as:

```text
relationship not specified
```

A declarative system should be able to express:

> "These two fields should deliberately have no linear relationship."

That gives the specification greater semantic precision.

# 14. What this means for realistic synthetic data

This is where the experiment becomes directly relevant to 021.

Imagine we eventually want:

```text id="3h7m9q"
CUSTOMER_SCORE
CREDIT_LIMIT
RISK_SCORE
RETENTION_SCORE
ORDER_VALUE
```

We could declare:

```text id="d9q4m2"
CUSTOMER_SCORE ↔ CREDIT_LIMIT     +0.75
CUSTOMER_SCORE ↔ RISK_SCORE      -0.60
RISK_SCORE ↔ RETENTION_SCORE      -0.40
```

FORGE could then:

1. construct the statistical graph
2. build the correlation matrix
3. determine whether it is feasible
4. generate the variables jointly
5. measure the resulting relationships
6. reject the dataset if the relationships aren't achieved

That is much closer to **statistically grounded synthetic data generation**.

# 15. What have we proven?

I would document the capability as:

> **FORGE can represent multiple declarative statistical relationships as a correlation graph, construct and validate the corresponding correlation matrix for mathematical feasibility, jointly generate related fields, and independently verify the achieved relationships while rejecting impossible or conflicting specifications.**

That is a strong architectural capability.

---

# 16. What have we NOT proven?

We should be precise here.

Q proves multi-field **correlation** relationships.

It does not yet prove that arbitrary statistical structures can be combined with:

* constraints
* conditional rules
* derived fields
* cross-entity relationships
* scenarios
* complex distributions
* record-level feasible regions

And that is exactly why the next experiments are important.

The really interesting question becomes:

```text id="k4p8n2"
Statistical graph
       +
Constraints
       +
Context
       +
Derived fields
       +
Conditional generation
```

Can these all coexist?

That is where R, R.1 and R.2 become much more significant.
