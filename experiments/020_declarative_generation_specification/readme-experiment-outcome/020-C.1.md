# Experiment 020-C.1: Expression Engine Validation Hardening

## 1. What were we trying to prove?

### In simple terms

020-C showed that FORGE had an expression engine, but it was not yet reliable enough.

We found three problems:

* `BETWEEN` did not behave correctly.
* `MATCH` did not behave correctly.
* Nested expressions did not behave correctly.

So we fixed the underlying behavior and asked a more complete question:

> **Can FORGE reliably evaluate declarative expressions, including true and false outcomes, nested expressions, errors, unsupported capabilities, and invalid vocabulary?**

This experiment was therefore about **hardening the expression engine**, not adding a new generation capability.

---

## 2. What did we actually do?

We tested the expression engine across several categories.

### Boolean results

We explicitly tested both outcomes:

```text
TRUE  → accepted correctly
FALSE → accepted correctly
```

This matters because a rule engine must not treat:

```text
FALSE
```

as an error.

A valid rule can legitimately evaluate to false.

### Comparisons

We retested:

```text
BETWEEN
```

with both:

```text
value inside bounds  → TRUE
value outside bounds → FALSE
```

### String matching

We tested:

```text
MATCH
```

with both valid and invalid values.

### Nested expressions

We tested expressions where one expression depends on another:

```text
Arithmetic
    ↓
Comparison
    ↓
Boolean result
```

### Conditional expressions

We tested:

```text
IF condition
THEN value
ELSE value
```

### Error handling

We deliberately gave the engine invalid inputs:

* missing operator
* missing operands
* unknown field
* division by zero
* unknown operator

### Capability boundaries

We also confirmed that valid but not-yet-executable capabilities such as:

```text
DERIVE
REFERENCE
```

remain **deferred**, rather than being silently executed or replaced with something else.

# 4. What does that actually mean?

In simple terms:

> **The expression engine can now tell the difference between a valid rule that evaluates to TRUE, a valid rule that evaluates to FALSE, and an invalid rule that should be rejected.**

That sounds small, but it is fundamental.

For example:

```text
CUSTOMER_SCORE > 80
```

could legitimately produce:

```text
TRUE
```

or:

```text
FALSE
```

Both are valid outcomes.

But:

```text
CUSTOMER_SCORE >>>
```

is not a valid expression.

That should produce an error.

The hardened engine now distinguishes these cases.

# 5. What changed compared with 020-C?

This is the important architectural story.

### 020-C

We discovered:

```text id="3qefom"
Some expressions
     ↓
incorrect behavior
```

Specifically:

```text
BETWEEN       FAIL
MATCH         FAIL
Nested rules  FAIL
```

### 020-C.1

We retested those areas and expanded the test boundary:

```text id="u7o4i9"
Valid expression
       │
       ├── TRUE  → valid result
       │
       └── FALSE → valid result

Invalid expression
       ↓
     ERROR

Valid but deferred capability
       ↓
    DEFERRED

Unknown vocabulary
       ↓
     ERROR
```

That gives the expression engine much stronger semantics.

---

# 6. Why is this important for FORGE?

The rest of the architecture will depend heavily on expressions.

For example:

### Constraints

```text
ORDER_VALUE >= 1000
```

### Conditional generation

```text
IF CUSTOMER_TYPE = PREMIUM
THEN CREDIT_LIMIT >= 5000
```

### Derived values

```text
NET_AMOUNT = ORDER_VALUE - DISCOUNT
```

### Statistical relationships

```text
RISK_SCORE correlated with CUSTOMER_SCORE
```

### Validation

```text
SHIPMENT_DATE >= ORDER_DATE
```

All of these ultimately depend on FORGE being able to evaluate declarative expressions correctly.

So this experiment strengthens the foundation for everything that follows.

---

# 7. What did we learn?

The important learning is:

> **A declarative expression engine needs explicit semantic handling for successful results, false results, invalid expressions, unsupported capabilities, and deterministic evaluation.**

We also established that **FALSE is a result, not a failure**.

That distinction becomes particularly important when expressions are used as constraints.

For example:

```text
CUSTOMER_SCORE > 80
```

returning:

```text
FALSE
```

doesn't mean the expression engine failed.

It means:

> The customer does not satisfy this condition.

The generation/validation layer can then decide what that means.

---

# 8. What have we now proven?

After C and C.1 together, we can make a much stronger statement.

### 020-C alone

> The expression engine was incomplete and had semantic correctness gaps.

### 020-C.1

> Those identified weaknesses were corrected, and the hardened expression engine successfully handled valid outcomes, nested expressions, conditional expressions, error conditions, deferred capabilities, invalid vocabulary, and deterministic evaluation.

That is a much more defensible architectural conclusion.

---

# 9. What have we NOT proven?

Even with **18/18 PASS**, we should not overclaim.

We have not yet proven:

* every one of the 41 executable operators exhaustively
* arbitrary deeply nested expressions
* very large expression trees
* expression performance at scale
* expression behavior across millions of records
* integration with the full constraint engine
* integration with statistical generation
* integration with cross-entity dependencies
* complete expression-based dataset generation

Those are later concerns.

```text id="m2ynbq"

   ↓
```

No silent fallback.
