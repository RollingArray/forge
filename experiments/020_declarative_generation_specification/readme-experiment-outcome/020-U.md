# Experiment 020-U: Declarative Specification Conflict Diagnosis

## 1. What were we trying to prove?

The question was:

> **When a declarative specification cannot be satisfied, can FORGE explain exactly why instead of simply failing generation?**

The intended architecture is:

```text
Declarative specification
        ↓
Requirement extraction
        ↓
Constraint / dependency graph
        ↓
Feasibility analysis
        ↓
Conflict diagnosis
        ↓
Actionable explanation
```

This is important because a generation engine that only says:

```text
Generation failed
```

is not particularly useful.

FORGE needs to be able to say:

> This requirement is impossible, these rules caused the conflict, this is the dependency path, and this is the feasible region that became empty.

That is what U validates.

# 3. The representative failure is exactly the kind we want FORGE to understand

The system deliberately creates an impossible requirement around:

```text
ORDER.ORDER_VALUE
```

The conflict is:

```text
FIELD_BOUND_MAX
ORDER.ORDER_VALUE >= CUSTOMER_VALUE
```

The resolved context becomes:

```text
minimum = 7000
maximum = 5000
```

Therefore:

```text
minimum > maximum
```

and the feasible region is:

```text
[7000, 5000]
```

which is empty.

FORGE identifies:

```text
type:
EMPTY_FEASIBLE_REGION
```

That's much better than a generic generation error.

---

# 4. It identifies the actual source rules

The diagnosis explicitly points to:

```text
FIELD_BOUND_MAX
ORDER_ABOVE_CUSTOMER
```

This is important because the system isn't just saying:

> "ORDER_VALUE is impossible."

It can identify **which declarative requirements created the impossibility**.

Conceptually:

```text
FIELD_BOUND_MAX
       │
       ├── maximum = 5000
       │
       ▼
 ORDER.ORDER_VALUE
       ▲
       │
ORDER_ABOVE_CUSTOMER
       │
       └── minimum = CUSTOMER_VALUE = 7000
```

Therefore:

```text
7000 <= ORDER_VALUE <= 5000
```

is impossible.

---

# 5. Dependency path also passed

The experiment reports:

```text
dependency path:
ORDER.ORDER_VALUE
```

This becomes much more valuable as specifications become more complex.

Imagine eventually having:

```text
CUSTOMER
   ↓
CUSTOMER_PROFILE
   ↓
ORDER
   ↓
ORDER_ITEM
   ↓
SHIPMENT
```

and a conflict somewhere downstream.

The diagnosis engine needs to understand how that requirement was reached.

U demonstrates that the architecture can carry that dependency context.

---

# 6. Cross-field and chained conflicts passed

This is important.

A simple conflict:

```text
A >= 100
A <= 50
```

is easy.

A more realistic engineering/business specification might have:

```text
A depends on B
B depends on C
C has a constraint
```

and the contradiction appears only after resolving the chain.

U explicitly tests:

> **Chained conflict: PASS**

and:

> **Cross-field conflict: PASS**

So the diagnosis architecture isn't limited to local field validation.

---

# 7. Conditional conflicts passed

This is another significant result.

A conflict can exist only under certain conditions:

```text
IF CUSTOMER_TYPE = PREMIUM
    ORDER_VALUE >= 10000

AND

ORDER_VALUE <= 5000
```

The specification may be valid for STANDARD customers but impossible for PREMIUM customers.

U validates:

> **Conditional conflict: PASS**

That connects directly to the conditional and scenario architecture we established earlier.

---

# 8. Multiple conflict detection passed

Real specifications may contain several independent problems.

For example:

```text
Conflict 1 → ORDER_VALUE
Conflict 2 → CREDIT_LIMIT
Conflict 3 → DISCOUNT
```

A useful diagnosis system shouldn't stop at the first error.

U validates:

> **Multiple conflict detection: PASS**

That makes the system much more useful for specification authors.

# 9. Feasible-region explanation passed

This is one of the strongest connections to R.2.

R.2 introduced:

```text

      ↓

      ↓
Generation
```

U now uses the same concept in the opposite direction:

```text
Specification
      ↓
Requirements
      ↓

      ↓

      ↓

```

So we have a common architectural abstraction:

```text
              FEASIBLE REGION
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
      Generation          Diagnosis
          │                   │
   Generate within       Explain when
     the region          region is empty
```

That is a particularly nice architectural outcome.

---

# 10. No hidden relaxation passed

This deserves emphasis.

When FORGE discovers:

```text
7000 <= ORDER_VALUE <= 5000
```

it does **not** silently decide:

```text
"Let's just generate 5000."
```

or:

```text
"Let's ignore the minimum."
```

Instead:

```text
Empty feasible region
        ↓
Generation blocked
        ↓
Conflict explained
```

Result:

> **No hidden relaxation: PASS**

That is exactly what we want from a system intended for engineering data.

---

# 11. No post-generation repair passed

Again:

> **No post-generation repair: PASS**

This reinforces one of the strongest architectural principles emerging from 020:

> **FORGE should solve the specification before generation rather than generate invalid data and repair it afterward.**

That principle now appears consistently across K.2, R.2, S, T, and U.

# 12. Generation blocking passed

The diagnosis isn't merely advisory.

When the specification is impossible:

```text
Specification
       ↓

       ↓
Impossible

BLOCK GENERATION
```

Result:

> **Generation blocking: PASS**

That makes U part of the generation safety architecture, not just a reporting feature.

# 13. Determinism passed

The same specification produces the same diagnosis.

Result:

> **Deterministic diagnosis: PASS**

That matters for reproducibility and debugging.

If an engineer fixes something and reruns the specification, they should be able to trust that differences in diagnosis correspond to differences in the specification, not arbitrary execution order.

# 16. No false-positive diagnosis passed

This is critical.

A diagnosis engine that reports conflicts for valid specifications would be almost as bad as one that misses real conflicts.

U validates:

> **No false-positive diagnosis: PASS**

So the system distinguishes between:

```text
Valid specification
       ↓
Allow generation
```

and:

```text
Invalid specification
       ↓
Block + diagnose
```

That distinction is fundamental.

# 17. What have we proven?

I would document the core outcome as:

> **FORGE can analyze declarative generation requirements for feasibility and provide deterministic, actionable diagnoses when conflicts occur. The diagnosis engine identifies direct, cross-field, chained, conditional, and multiple conflicts, explains the resulting feasible region, references the source rules and dependency path, blocks invalid generation without hidden relaxation or post-generation repair, and safely rejects invalid references.**

That is a strong architectural result.
