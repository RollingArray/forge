# Experiment 020-R.2: Constraint-Conditioned Statistical Generation

## 1. What were we trying to prove?

The question was:

> **Can FORGE generate a statistically controlled value directly inside the feasible region created by the constraints and the current record context?**

This is different from:

```text
Generate
   ↓
Check constraint
   ↓
Repair / reject
```

The intended model is:

```text
Source generation
       ↓
Record-level context
       ↓
Feasible target region
       ↓
Statistical generation
       ↓
Independent validation
```

That distinction is fundamental to the FORGE hypothesis.

---

# 2. The important difference from R.1

R.1 established that we needed a unified feasibility model.

But R.1 still had:

```text
Constraint preservation: FAIL
```

R.2 makes the feasible region **record-specific**.

For example:

```text
CUSTOMER_SCORE = 20
        ↓
CREDIT_LIMIT
[1000, 10000]
```

but:

```text
CUSTOMER_SCORE = 60
        ↓
CREDIT_LIMIT
[3000, 10000]
```

and:

```text
CUSTOMER_SCORE = 80
        ↓
CREDIT_LIMIT
[5000, 10000]
```

The allowed generation space changes based on the actual context of the record.

That is much closer to how real business rules work.

# 9. Multiple constraints passed

The experiment explicitly validates:

> **Multiple constraints: PASS**

That means the target field can be constrained by more than one requirement.

For example:

```text id="6p3q8m"
CREDIT_LIMIT >= CUSTOMER_SCORE × 50
CREDIT_LIMIT <= CUSTOMER_SCORE × 200
CREDIT_LIMIT <= 10000
```

The generator needs to find their intersection.

Conceptually:

```text id="9r4m7q"
Constraint A
      \
       \
Constraint B → Feasible region
       /
Constraint C
```

R.2 demonstrates that this works in the tested cases.

# 10. Impossible record-region blocking is especially important

There are two different kinds of impossibility:

### Specification-level impossibility

```text id="8q2m6p"
MINIMUM = 7000
MAXIMUM = 5000
```

The specification itself is impossible.

### Record-level impossibility

The specification may be valid generally, but a particular record context can make it impossible.

For example:

```text id="3v7m1q"
CUSTOMER_SCORE = 95

Constraint:
CREDIT_LIMIT >= 10000
CREDIT_LIMIT <= 5000
```

The specification may work for many records but fail for this particular context.

R.2 explicitly tests:

> **Impossible record-region blocking: PASS**

This is a very valuable capability.

---

# 11. No post-generation repair passed

This is perhaps one of the strongest architectural results.

The experiment confirms:

> **No post-generation repair: PASS**

So the engine isn't doing:

```text id="4m8q7p"
Generate bad value
       ↓
Detect violation
       ↓
Modify value
       ↓
Pretend it was generated correctly
```

Instead:

```text id="7q2m9v"
Determine feasible region
       ↓
Generate inside region
```

That preserves the provenance and statistical semantics of the generated value.

This becomes very important later when we use the provenance model from 020-T.

# 15. What have we now proven?

I would document R.2 as:

> **FORGE can perform record-level constraint-conditioned statistical generation by deriving feasible target regions from field bounds, cross-field constraints, and conditional rules before sampling. ---

# 16. What have we NOT proven?

We should still be careful.

R.2 proves this architecture for the tested generation model.

It does **not** prove that every arbitrary constraint and statistical distribution can be combined.

For example, there will eventually be cases involving:

```text id="5n8q2m"
complex distributions
      +
nonlinear constraints
      +
multiple correlated variables
      +
cross-entity context
      +
scenario overrides
```

Those combinations may still have feasibility or numerical challenges.

But that's exactly where 020-S becomes important.
