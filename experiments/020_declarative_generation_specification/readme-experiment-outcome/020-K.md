# Experiment 020-K: Constraint-Aware Generation

## 1. What were we trying to prove?

### In simple terms

A dataset can be structurally valid and still be wrong.

For example, suppose the specification says:

```text
CUSTOMER_SCORE >= 50
```

A normal random generator might produce:

```text
CUSTOMER_SCORE = 32
```

The value is perfectly valid as an integer.

But it violates the business requirement.

A traditional approach would be:

```text id="z8r6w2"
Generate value
      ↓
Check constraint
      ↓
Invalid
      ↓
Repair / regenerate
```

But the FORGE hypothesis is stronger.

We want:

```text id="8s7q2p"
Constraint
    ↓
Analyze constraint
    ↓
Determine feasible region
    ↓
Generate directly inside region
    ↓
Validate
```

So 020-K asks:

> **Can constraints become part of generation itself?**

---

# 2. What did we test?

The experiment tested three kinds of constraints:

### Field constraints

Constraints directly on a field.

For example:

```text id="y7s1g2"
CREDIT_LIMIT >= 5000
```

### Cross-field constraints

Constraints involving multiple fields.

For example:

```text id="p3w6n8"
MAX_AMOUNT >= MIN_AMOUNT
```

or:

```text id="k8d1r4"
ORDER_VALUE >= CUSTOMER_VALUE
```

### Conditional constraints

Rules such as:

```text id="g9v2x5"
IF CUSTOMER_TYPE = PREMIUM
THEN CREDIT_LIMIT >= 5000
```

The experiment also deliberately introduced impossible specifications to verify that FORGE would block them rather than silently relax them.

---

# 3. What happened?

The result was:

```text id="4j5s8q"
Field constraints              FAIL
Cross-field constraints        FAIL
Conditional constraints        PASS
Direct conflict blocking       PASS
Cross-field conflict blocking  PASS
Reproducibility                PASS
Validation integrity           FAIL
```

Only:

```text id="j4k7n2"
4 / 7 PASS
```

So:

**Overall: FAIL**

---

# 4. This failure is actually very informative

The most important thing is that **conflict detection already works**.

FORGE can recognize:

> "These requirements cannot simultaneously be satisfied."

And it can block the situation.

But the harder capability is not working reliably:

> **Using valid constraints to shape the generation region before a value is generated.**

So we have an important split:

```text id="7s4k1m"
Can FORGE detect an impossible constraint?
             │
             ▼
            YES

Can FORGE generate directly
inside a valid constraint region?
             │
             ▼
            NOT YET
```

That distinction is critical.

---

# 5. Why is this different from validation?

Consider:

```text id="9p2r6s"
Constraint:
CREDIT_LIMIT >= 5000
```

A validation-only architecture does:

```text id="v6x8q1"
Generate CREDIT_LIMIT
        ↓
  3275
        ↓
Validate
        ↓
  FAIL
```

That does not really solve the generation problem.

A constraint-aware generator should instead determine:

```text id="w3m7c9"
Possible values:
5000 → 10000
```

and then sample directly:

```text id="2n5q8s"
CREDIT_LIMIT = 7342
```

So the constraint is part of **generation planning**, not merely post-generation validation.

020-K shows that we haven't fully achieved this yet.

---

# 6. What does the PASS on conditional constraints tell us?

This is interesting.

The conditional model appears to work better than the basic field/cross-field constraint generation.

For example:

```text id="d1p5r8"
IF CUSTOMER_TYPE = PREMIUM
THEN CREDIT_LIMIT >= 5000
```

was successfully handled.

That tells us the expression and conditional infrastructure built in 020-C/C.1 is useful.

But general feasible-region generation is not yet mature.

So we should not conclude:

> "Constraints don't work."

A more accurate conclusion is:

> **Conditional rule evaluation works, but general constraint-aware generation and cross-field feasible-region construction remain incomplete.**

---

# 7. Why did validation integrity fail?

This is probably the most important failure from an architectural perspective.

The pipeline is supposed to be:

```text id="v2m6n9"
Constraint
   ↓
Analysis
   ↓
Feasible region
   ↓
Generation
   ↓
Validation
```

But the results indicate that the generated values are not consistently aligned with the constraint analysis.

So there is currently a gap between:

```text id="k5x2m7"
Constraint interpretation
```

and:

```text id="r7q4n1"
Generation behavior
```

That means the constraint engine and generator are not yet sufficiently integrated.

---

# 8. What did we learn?

The major learning is:

> **Constraint validation and constraint-aware generation are two different capabilities and must be architecturally separated.**

We need at least:

```text id="z8c4m1"
Constraint Parser
      ↓
Constraint Representation
      ↓
Feasibility Analysis
      ↓
Feasible Generation Region
      ↓
Generation Planner
      ↓
Generator
      ↓
Independent Validator
```

The validator must remain independent.

Otherwise we could accidentally create a system that says:

> "I generated it, therefore it must be valid."

We want the generator and validator to independently establish correctness.

---

# 9. This explains why 020-K.1 and K.2 were needed

This failure directly motivates the experiments you subsequently ran.

The architecture needs to move from:

```text id="c5m8p2"
Constraint
   ↓
Check it
```

to:

```text id="g7q3w1"
Constraint
   ↓
Propagate it
   ↓
Determine feasible region
   ↓
Plan generation
   ↓
Generate directly
```

That is what K.1 and K.2 were testing.

And importantly:

* **020-K.1** exposed remaining weaknesses in cross-field and chained propagation.
* **020-K.2** achieved **10/10 PASS** for constraint-driven generation planning.

So 020-K should not be considered the final constraint result.

It is the **failure that caused the architecture to evolve**.

---

# 10. What have we NOT proven?

At this point, we cannot claim:

> "FORGE supports general constraint-aware generation."

020-K does not establish that.

What we can claim is:

> FORGE can represent constraints, evaluate conditional constraints, detect direct and cross-field conflicts, and reproduce generation deterministically, but the initial constraint-aware generation implementation does not yet reliably preserve field and cross-field constraints.

That is the scientifically honest conclusion.

---

# 11. Architectural Outcome

The baseline 020-J architecture:

```text id="a7v4c9"
Specification
      ↓
Planning
      ↓
Generation
      ↓
Validation
```

needs to evolve into:

```text id="m9k2r5"
Specification
      ↓
Requirement Extraction
      ↓
Constraint Analysis
      ↓
Feasibility Analysis
      ↓
Generation Planning
      ↓
Constraint-Aware Generation
      ↓
Independent Validation
```

And this becomes a major architectural branch of FORGE.

---

# 12. Resulting FORGE Capability

For **020-K specifically**, I would document the capability conservatively:

> **FORGE can represent declarative constraints, evaluate conditional constraints, detect infeasible specifications, and maintain deterministic generation, but the initial implementation does not yet reliably integrate field and cross-field constraints into the generation process.**

Then reference the follow-up experiments as the architectural response.
