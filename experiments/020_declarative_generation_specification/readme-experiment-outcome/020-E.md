# Experiment 020-E: Declarative Multi-Field Record Generation

## 1. What were we trying to prove?

### In simple terms

020-D proved that FORGE can generate individual fields.

But a real dataset is not a collection of unrelated fields. A record contains many fields together:

```text
CUSTOMER
├── CUSTOMER_ID
├── CUSTOMER_TYPE
├── COUNTRY
├── CREDIT_LIMIT
└── IS_ACTIVE
```

So the next question was:

> **Can FORGE generate complete records from a declarative specification, while keeping the generation generic and independent of how the fields happen to be listed?**

The last part is important.

If I write:

```text
CUSTOMER_ID
CUSTOMER_TYPE
COUNTRY
CREDIT_LIMIT
IS_ACTIVE
```

or rearrange them as:

```text
IS_ACTIVE
CREDIT_LIMIT
COUNTRY
CUSTOMER_TYPE
CUSTOMER_ID
```

the generated dataset should not change simply because the specification was written in a different order.

---

# 2. What did we actually do?

We asked FORGE to generate records for two different entities:

### CUSTOMER

```text
CUSTOMER_ID
CUSTOMER_TYPE
COUNTRY
CREDIT_LIMIT
IS_ACTIVE
```

### PRODUCT

```text
PRODUCT_ID
PRODUCT_TYPE
UNIT_PRICE
PRODUCT_SCORE
CREATED_DATE
```

FORGE generated **10 records for each entity**.

We then tested four things:

1. Can FORGE generate complete records?
2. Can the same generic engine handle different entities?
3. Does changing field declaration order change the result?
4. Does the same specification and seed reproduce the same result?

---

# 3. What happened?

Three areas passed:

```text id="r6zv9t"
CUSTOMER generation       PASS
PRODUCT generation        PASS
Entity agnosticism        PASS
Reproducibility           PASS
```

But one important test failed:

```text id="y04c5r"
Field-order independence  FAIL
```

Therefore:

```text id="1k0o2m"
Overall: FAIL
```

---

# 4. What did FORGE successfully do?

It generated complete multi-field records.

For example:

```text id="f8e4e0"
{
  'CUSTOMER_ID': 'CUS-1',
  'CUSTOMER_TYPE': 'STANDARD',
  'COUNTRY': 'US',
  'CREDIT_LIMIT': 8252.37,
  'IS_ACTIVE': True
}
```

And for a completely different entity:

```text id="p7c0g4"
{
  'PRODUCT_ID': 'PRD-100',
  'PRODUCT_TYPE': 'SPECIAL',
  'UNIT_PRICE': 3386.73,
  'PRODUCT_SCORE': 68.22,
  'CREATED_DATE': 2026-01-01
}
```

This proves that 020-D's field generation capability can be composed into actual records.

That is a meaningful step forward.

---

# 5. What failed?

The failure was:

> **Field declaration order changes the generated result.**

This is important because the specification should describe **what the dataset should look like**, not accidentally dictate an execution order unless an explicit dependency exists.

Consider:

```text id="3pfy4b"
Field specification:

A
B
C
D
```

versus:

```text id="o9p3u1"
D
B
A
C
```

If A, B, C and D are independent, FORGE should be free to generate them in either order and still produce the same deterministic result for the same seed.

Instead, the experiment showed that the current implementation's random generation is influenced by the order in which fields are processed.

---

# 6. What does that actually mean?

This is a subtle but important distinction.

It does **not** necessarily mean the generated values are wrong.

It means the generation engine currently behaves somewhat like:

```text id="pp9r3j"
Seed 42
   ↓
Generate Field A
   ↓
Random stream advances
   ↓
Generate Field B
   ↓
Random stream advances
   ↓
Generate Field C
```

If we change the field order:

```text id="qdyf4w"
Seed 42
   ↓
Generate Field C
   ↓
Random stream advances
   ↓
Generate Field A
   ↓
Random stream advances
   ↓
Generate Field B
```

the random values assigned to the fields change.

So the seed is deterministic, but the **deterministic result is coupled to specification ordering**.

That is not what we ultimately want.

---

# 7. Why is this architecturally important?

Because FORGE is supposed to be **declarative**.

The user should be saying:

> "Generate these fields with these properties."

They should not have to worry about:

> "Put this field before that field because otherwise the random stream changes."

That would make specification order an accidental part of the generation semantics.

We want:

```text id="5h1m4r"
Specification
     │
     ├── Field A
     ├── Field B
     ├── Field C
     └── Field D
```

to mean the same thing as:

```text id="a0z4yy"
Specification
     │
     ├── Field D
     ├── Field A
     ├── Field C
     └── Field B
```

when there are no declared dependencies.

---

# 8. What did we learn?

020-E exposed an important architectural requirement:

> **Deterministic generation is not sufficient. FORGE also needs order-independent determinism.**

There are actually two different properties:

### Reproducibility

Same specification + same seed:

```text
A → B → C
```

produces the same result every time.

020-E:

**PASS**

### Order independence

Same specification + same seed:

```text
A → B → C
```

and:

```text
C → A → B
```

should produce equivalent results when no dependency exists.

020-E:

**FAIL**

This is an excellent distinction for the final architecture document.

---

# 9. What should the architecture eventually do?

The likely direction is to give each field its own deterministic generation namespace rather than relying entirely on one shared sequential random stream.

Conceptually:

```text id="l2x9b3"
                    Seed = 42
                       │
              ┌────────┼────────┐
              ▼        ▼        ▼
           FIELD:A  FIELD:B  FIELD:C
              │        │        │
              ▼        ▼        ▼
           Random    Random   Random
           stream    stream   stream
```

For example:

```text id="d5x6ml"
Seed
 +
Entity
 +
Field
 +
Generation context
        ↓
Deterministic field stream
```

Then changing the order of fields would not change the random stream assigned to each field.

This is also consistent with what we later saw in **020-T**, where provenance used namespaces such as:

```text
FIELD:ORDER:NET_ORDER_VALUE
```

That is a useful architectural direction.

---

# 10. What have we NOT proven?

020-E does not yet prove:

* relationships between fields
* dependencies between fields
* cross-field constraints
* relationships between entities
* conditional generation
* derived fields
* statistical relationships
* population behavior
* scenario behavior

And importantly:

> **We have not yet solved order-independent deterministic generation.**

That becomes an explicit architectural requirement coming out of this experiment.

---

# 11. Architectural Outcome

### Before 020-E

We had:

```text id="q83z3q"
Field generation
      ↓
Multi-field record generation
```

### What 020-E exposed

```text id="9e6n0u"
Multi-field generation
        ↓
Random stream
        ↓
Field order affects values
```

### Architectural requirement discovered

```text id="nqv24c"
Declarative specification
        ↓
Canonical / dependency-aware planning
        ↓
Field-specific deterministic generation
        ↓
Order-independent results
```

This will become important when we build dependency planning later.

---

# 12. Resulting FORGE Capability

The honest outcome is:

> **FORGE can generically generate complete multi-field records and reproduce them with a fixed seed, but the current generation model is sensitive to field declaration order.**

So this is **not yet a complete declarative record-generation capability**.

The failure gives us a concrete requirement:

> **Independent fields must generate deterministically regardless of their declaration order.**
