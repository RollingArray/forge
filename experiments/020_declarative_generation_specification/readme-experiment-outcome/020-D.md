# Experiment 020-D: Declarative Field Generation

## 1. What were we trying to prove?

### In simple terms

By this point, FORGE could:

* understand a declarative specification
* check whether requested capabilities are executable
* evaluate declarative rules and expressions

The next question was more concrete:

> **Can FORGE actually take a field definition from the specification and generate values for it, without caring what the field is called?**

For example, if the specification says:

```text
FIELD_INTEGER
  type = INTEGER
  strategy = RANDOM
  distribution = DISCRETE_UNIFORM
```

FORGE should generate integers.

If another specification says:

```text
CUSTOMER_SCORE
  type = INTEGER
  strategy = RANDOM
  distribution = DISCRETE_UNIFORM
```

the generation behavior should be the same.

The field name should not secretly contain generation logic.

---

# 2. What did we actually do?

We tested generic generation across **15 different field definitions**, covering the executable type, strategy, and distribution combinations available at this stage.

Examples included:

```text
INTEGER       → random discrete values
DECIMAL       → random uniform values
FLOAT         → normal distribution
STRING        → constant value
BOOLEAN       → categorical generation
DATE          → constant date
DATETIME      → constant datetime
TIME          → constant time
CATEGORICAL   → categorical generation
ENUM          → categorical generation
CODE          → sequential generation
IDENTIFIER    → sequential generation
PERCENTAGE    → uniform generation
CURRENCY      → uniform generation
NULL          → null generation
```

We also checked two important properties:

### Field agnosticism

Would the same specification logic work if we changed the field name?

### Reproducibility

Would using the same seed produce the same generated values?

# 4. What does that actually mean?

This is the first experiment in the 020 series where we can say:

> **FORGE is actually generating values from declarative field definitions.**

That is an important milestone.

We have moved beyond validating the specification and capability boundaries.

The basic path now works:

```text
Specification
      ↓
Field definition
      ↓
Generation strategy
      ↓
Distribution
      ↓
Generated value
```

And it works without embedding the field name into the generation logic.

---

# 5. Why is field agnosticism important?

This is one of the most important results in this experiment.

The test showed:

> **The generation behavior is driven by the field specification, not by the field's name.**

That means FORGE is moving toward a genuinely generic generation engine.

We don't want code like:

```python
if field_name == "CUSTOMER_SCORE":
    generate_score()
elif field_name == "CREDIT_LIMIT":
    generate_credit()
elif field_name == "QUANTITY":
    generate_quantity()
```

That would quickly become impossible to maintain.

Instead, the architecture is:

```text
Field
  │
  ├── Type
  ├── Strategy
  └── Distribution
        │
        ▼
Generic Generator
        │
        ▼
Value
```

That is much closer to the hypothesis behind FORGE.

---

# 6. What did we learn?

We established three important things.

### 1. Field generation can be generic

The engine can generate different types of fields using the same underlying generation architecture.

### 2. The specification controls behavior

The behavior comes from:

```text
type
strategy
distribution
parameters
```

rather than the field name.

### 3. Reproducibility is working at field-generation level

With the seeded generation:

```text
Seed = 42
```

FORGE can reproduce the generation behavior.

That gives us a foundation for deterministic dataset generation later.

---

# 7. What have we NOT proven?

This is where we need to remain disciplined.

020-D proves **field-level generation**, not dataset-level generation.

We have not yet proven:

* relationships between fields
* relationships between entities
* primary/foreign key integrity
* cross-field constraints
* conditional generation
* derived values
* statistical relationships between fields
* realistic distributions at dataset scale
* population/nullability behavior across a dataset
* scenario-driven generation
* generation of a complete business dataset

So the result is strong, but deliberately narrow.
