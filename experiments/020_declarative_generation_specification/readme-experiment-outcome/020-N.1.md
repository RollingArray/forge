# Experiment 020-N.1: Cross-Entity Context Resolution

## 1. Why did we run this?

020-N showed something important:

> The individual generation capabilities work, and the planner works, but the integrated system struggles when information has to move across entities.

N.1 isolates that specific problem.

The question is:

> **Can FORGE safely resolve a value from another entity and use it as generation context without relying on entity order, field order, or hidden fallback behavior?**

The experiment uses this model:

```text
Current Entity
      ↓
Relationship Path
      ↓
Parent Entity
      ↓
Parent Field
```

For example:

```text
SHIPMENT.DELIVERY_DATE
        =
ORDER.ORDER_DATE
        +
SHIPMENT.DELIVERY_DAYS
```

So `SHIPMENT` needs information from `ORDER`.

---

# 3. The most important result

The most important test is:

> **Cross-entity derived value: PASS**

This means FORGE can do something like:

```text
ORDER
 └── ORDER_DATE = 2026-01-10
          │
          ▼
SHIPMENT
 ├── DELIVERY_DAYS = 5
 │
 └── DELIVERY_DATE = 2026-01-15
```

The value isn't independently generated.

It is resolved from:

```text
ORDER.ORDER_DATE
        +
SHIPMENT.DELIVERY_DAYS
```

That is exactly the kind of behavior required for realistic relational datasets.

---

# 4. Multi-level context is even more significant

The experiment also passed:

> **Multi-level context: PASS**

This means the context model isn't limited to:

```text
Child → Parent
```

It can resolve through a longer relationship path.

Conceptually:

```text
SHIPMENT
    ↓
ORDER
    ↓
CUSTOMER
    ↓
CUSTOMER_PROFILE
```

This is important because enterprise data rarely consists of isolated two-table relationships.

---

# 5. Why entity-order independence matters

This is one of the strongest architectural properties.

Suppose the specification lists:

```text
CUSTOMER
ORDER
SHIPMENT
```

versus:

```text
SHIPMENT
CUSTOMER
ORDER
```

The result should not depend on declaration order.

The relationship graph should determine the required context.

The experiment confirms:

> **Entity-order independence: PASS**

So we are moving toward:

```text
Specification order
        ≠
Execution semantics
```

That is a core requirement of a declarative system.

---

# 6. Field-order independence also passed

The same principle applies within an entity.

If:

```text
ORDER_DATE
DELIVERY_DAYS
DELIVERY_DATE
```

becomes:

```text
DELIVERY_DATE
ORDER_DATE
DELIVERY_DAYS
```

the generator should still understand that `DELIVERY_DATE` depends on the other values.

The result:

> **Field-order independence: PASS**

confirms that the resolution mechanism is context-driven rather than declaration-order-driven.

---

# 7. Safety behavior is particularly good

The experiment deliberately tested invalid situations.

### Unknown field

```text
ORDER.UNKNOWN_DATE
```

Result:

> PASS

The generator blocks it.

### Missing relationship

If the specification asks:

```text
SHIPMENT → ORDER
```

but no such relationship exists:

> PASS

Generation is blocked.

### Ambiguous relationship

If multiple paths could resolve the same reference:

> PASS

The system does not guess.

### No fallback generation

This is perhaps the most important safety property.

If the requested context cannot be resolved, FORGE does **not** say:

> "I'll just generate something."

It blocks.

That preserves the declarative contract.

# 9. What N.1 does NOT prove yet

This distinction is important.

N.1 proves:

> **Cross-entity context resolution works.**

It does not yet prove:

```text
Cross-entity context
       +
constraints
       +
statistics
       +
conditional generation
       +
derived fields
       +
relationships
```

all work together.

That is the remaining integration challenge.

For example:

```text
CUSTOMER.CUSTOMER_SCORE
        ↓
ORDER.ORDER_VALUE
        ↓
constraint
        ↓
statistical generation
        ↓
DISCOUNT
        ↓
NET_ORDER_VALUE
        ↓
SHIPMENT.SHIPPING_COST
```

That is a much harder integrated scenario.

---

# 10. Architectural outcome

N.1 gives us a reusable **context-resolution layer**:

```text
                     Generation Context
                           │
                           ▼
                    Relationship Path
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
        Local field     Parent field   Multi-level
             │             │             │
             └─────────────┼─────────────┘
                           ▼
                    Resolved Context
                           │
                           ▼
                Derived / Conditional /
                Constraint / Statistical
                     Generation
```

This is a valuable architectural component.

It means downstream generators don't need to independently figure out how to navigate relationships.

They can ask the context layer:

```text
"Give me ORDER.ORDER_DATE for this SHIPMENT."
```

and either receive a deterministic value or an explicit failure.

---

# 11. Resulting capability statement

I would document N.1 as:

> **FORGE can safely resolve local, parent, cross-entity, and multi-level field context through declared relationship paths, independent of entity or field declaration order, while deterministically blocking unknown, missing, ambiguous, or otherwise unresolved references without fallback generation.**

That is a strong result.
