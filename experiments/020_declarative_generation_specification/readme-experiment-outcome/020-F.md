# Experiment 020-F: Population and Nullability

## 1. What were we trying to prove?

### In simple terms

So far, we have established that FORGE can generate values and complete records.

But a real dataset is not simply:

> "Generate a value for every field in every record."

Real data has **missing values** and **different population rates**.

For example:

```text
CUSTOMER_EMAIL
  → populated for 95% of customers

PHONE_NUMBER
  → populated for 70%

SECONDARY_ADDRESS
  → optional

CUSTOMER_ID
  → always populated
```

So we asked:

> **Can FORGE declaratively control how often a field exists and whether a field is allowed or required to be NULL?**

---

# 2. What did we actually do?

We tested two related concepts.

### Population

Population controls **whether a value should be generated at all**.

FORGE supports:

```text
POPULATION_COUNT
POPULATION_RATE
```

For example:

```text
POPULATION_RATE = 0.80
```

means roughly:

> Generate this field for 80% of the records.

### Nullability

Nullability controls what happens when a field is not populated or when NULL is otherwise permitted.

The experiment tested:

```text
ALWAYS
NEVER
NULLABLE
NOT_NULL
OPTIONAL
```

These are deliberately represented as declarative semantics rather than custom generation code.

# 4. What does that actually mean?

In simple terms:

> **FORGE can now control not only what value gets generated, but whether a value should be present in the first place.**

That is an important distinction.

For example, these are different requirements:

```text id="a7cvzg"
CUSTOMER_ID
  → must always exist
```

versus:

```text id="mnyvdi"
EMAIL
  → populated 90% of the time
```

versus:

```text id="j6fjzh"
SECONDARY_PHONE
  → optional
```

The generation engine now has declarative concepts for representing these differences.

---

# 5. Why is this important for real datasets?

This is one of the first experiments that moves FORGE closer to **realistic data generation**.

Real enterprise datasets are rarely 100% populated.

A synthetic dataset where every field is always filled would often be unrealistic.

Consider:

```text id="8k1j5s"
CUSTOMER
────────────────────────
CUSTOMER_ID       100%
CUSTOMER_TYPE     100%
COUNTRY            98%
EMAIL              91%
PHONE              76%
ADDRESS_LINE_2     43%
```

Those population patterns can matter significantly when synthetic data is used for:

* testing
* analytics
* application development
* data pipelines
* migration testing
* AI/ML training
* data-quality testing

020-F establishes that population behavior itself can be part of the declarative specification.

---

# 6. What did we learn?

The key learning is:

> **Population and nullability are generation semantics, not merely validation rules.**

That means FORGE can distinguish between:

```text id="2a3b5c"
"Generate a value."

"Do not generate a value."

"Generate a value unless optional."

"NULL is allowed."

"NULL is forbidden."

"Generate this field for approximately 80% of records."
```

These are different requirements and should remain explicitly represented in the specification.

---

# 7. An important architectural distinction

Population and nullability should not be collapsed into one concept.

For example:

```text id="y2j8s7"
Population
    ↓
Should this field participate in generation?
```

while:

```text id="1g5lks"
Nullability
    ↓
Is NULL an acceptable resulting value?
```

That gives us a cleaner conceptual model:

```text id="3q2y2x"
Field
 │
 ├── Population
 │      └── Should it exist?
 │
 ├── Nullability
 │      └── Can it be NULL?
 │
 └── Generation
        └── What value should it have?
```

This separation will become useful later when we combine population with constraints and statistical generation.

---

# 8. Determinism also passed

This experiment confirms that population behavior is compatible with the deterministic generation architecture established in 020-E.1.

That means:

```text id="1j72m3"
Same seed
+
Same specification
        ↓
Same population behavior
```

And field ordering does not alter that behavior:

```text id="6t1w9k"
Field order independence → PASS
```

This is important because population decisions themselves often involve randomness.

We don't want:

```text id="xq7j3c"
Move field
   ↓
Different records become populated
```

The experiment confirms that the current implementation avoids that problem.

---

# 9. What have we NOT proven?

020-F does not yet prove:

* realistic population rates at large scale
* statistical fidelity of missingness patterns
* correlations between missingness and other fields
* conditional population
* population dependencies between entities
* whether missingness is **MCAR, MAR, or MNAR**
* interaction between nullability and complex constraints

For example, we have not yet established behavior such as:

```text id="h8g6df"
IF CUSTOMER_TYPE = PREMIUM
    → EMAIL population = 100%

ELSE
    → EMAIL population = 80%
```

That is a more advanced conditional population requirement.

So this experiment establishes the **basic population/nullability foundation**, not complete missing-data modeling.

---

# 10. Architectural Outcome

The FORGE field model now has another explicit dimension:

```text id="0e5qz6"
                    FIELD
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   Population     Nullability    Generation
        │             │             │
        ▼             ▼             ▼
   Should exist?   NULL allowed?   What value?
```

This is cleaner than treating missing values as an accidental side effect of generation.

---

# 11. Resulting FORGE Capability

> **FORGE can declaratively control field population and nullability, including population counts, population rates, required/optional semantics, deterministic behavior, and safe handling of invalid configurations.**
