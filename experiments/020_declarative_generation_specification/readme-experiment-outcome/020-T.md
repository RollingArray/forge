# Experiment 020-T: Declarative Generation Provenance

## 1. What were we trying to prove?

The provenance architecture is:

```text
Specification
      ↓
Generation plan
      ↓
Generated value
      ↓
Provenance node
      ↓
Dependency lineage
```

This means the generated dataset is not treated as an opaque collection of numbers.

Each value can carry an explanation of its origin.

That is a very important distinction for FORGE.

---

Unlike some of the earlier focused experiments, T actually created:

```text
CUSTOMER:   100 records
PRODUCT:     50 records
ORDER:      200 records
```

Total:

```text
350 dataset records
```

And it produced:

```text
1,100 provenance nodes
```

with:

> **100% provenance coverage**

That is already a meaningful demonstration.

# 3. What kinds of provenance were tested?

The experiment validates provenance for:

```text
Direct generation
Statistical generation
Constraint-conditioned generation
Conditional generation
Derived fields
Relationships
Cross-entity lineage
Multi-level lineage
```

This is important because provenance isn't limited to:

> "This number was randomly generated."

It can explain more complex generation paths.

---

# 4. The representative explanation is exactly what we want

The experiment gives us:

```text
ORDER.NET_ORDER_VALUE [record=0]

value:
6090.810735144867

generation type:
DERIVED

specification:
DERIVED:NET_ORDER_VALUE

seed:
42

seed namespace:
FIELD:ORDER:NET_ORDER_VALUE
```

And then:

```text
rule:
  name: NET_ORDER_VALUE
  operation: SUBTRACT
  expression:
    ORDER_VALUE SUBTRACT DISCOUNT
```

with the actual dependencies:

```text
ORDER.ORDER_VALUE[0]
    = 6106.156151397033

ORDER.DISCOUNT[0]
    = 15.345416252165261
```

So we can reconstruct:

```text
6106.156151397033
        -
15.345416252165261
        =
6090.810735144867
```

That is a genuine explanation.

---

# 5. Why this is more important than it initially looks

Imagine an engineer asks:

> "Why is this order's net value $6,090.81?"

A conventional synthetic-data generator might answer:

> "It was generated."

FORGE can answer:

```text
NET_ORDER_VALUE
       ↓
DERIVED
       ↓
ORDER_VALUE - DISCOUNT
       ↓
ORDER_VALUE = 6106.156...
DISCOUNT   = 15.345...
       ↓
6090.810...
```

And it can point back to the specification and generation context.

That changes the trust model significantly.

# 7. Dataset/provenance consistency passed

This validates that the provenance isn't merely a separate log that can drift away from the dataset.

The experiment checks that the provenance corresponds to the actual generated values.

Result:

> **Dataset/provenance consistency: PASS**

This is critical.

We want:

```text
Dataset
   ↕
Provenance
```

not:

```text
Dataset       Provenance
   ↓              ↓
Value A        Value A'
```

---

# 8. Mutated value detection passed

This is one of my favorite tests in T.

The experiment deliberately changes a generated value and verifies that provenance detects the inconsistency.

Result:

> **Mutated value detection: PASS**

That means provenance can act as an integrity mechanism, not just an explanatory record.

Conceptually:

```text
Original value
      +
Original provenance
      ↓
MATCH
```

but:

```text
Mutated value
      +
Original provenance
      ↓
MISMATCH → DETECTED
```

That's valuable for an engineering system.

---

# 12. Provenance does not change the dataset

This passed:

> **Provenance does not change dataset: PASS**

This is an important architectural separation.

Provenance is observational.

It should not alter the generation semantics.

The desired model is:

```text
                Generation
                 /       \
                /         \
          Dataset       Provenance
```

rather than:

```text
Generation
    ↓
Provenance logic
    ↓
Dataset
```

The latter risks making explainability part of the generation behavior.

---

# 13. Specification references passed

This is also critical.

A provenance record isn't useful if it only says:

```text

```

We want:

```text

      ↓
generation rule
      ↓
specification reference
```

The experiment confirms:

> **Specification references: PASS**

So provenance is tied back to the declarative source.

# 17. What have we proven?

I would document 020-T as:

> **FORGE can produce deterministic, complete provenance for generated data, including direct, statistical, constraint-conditioned, conditional, derived, relational, cross-entity, and multi-level generation paths. Provenance remains consistent with the dataset, references the originating specification and seed context, detects mutations and broken lineage, and does not alter the generated dataset.**

That's a strong result.

---

# 18. What have we NOT proven?

We should be careful here too.

T proves provenance for the tested generation architecture.

It does not yet prove that provenance is:

* optimized for very large datasets
* efficient at millions/billions of records
* human-friendly as a UI
* compact enough for production-scale storage
* version-aware across changing specifications

Those are probably later product concerns.

For 020, the important thing is that **the provenance model itself works**.
