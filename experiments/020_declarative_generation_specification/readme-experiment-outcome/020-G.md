# Experiment 020-G: Declarative Identity and Uniqueness

## 1. What were we trying to prove?

### In simple terms

So far, FORGE can generate fields, records, population patterns, and deterministic values.

But a real dataset has identity.

For example:

```text
CUSTOMER_ID
```

isn't just another string.

It may mean:

> Every customer must have a unique identifier.

Similarly:

```text
ORDER_ID
```

must identify an order, while:

```text
CUSTOMER_ID
```

inside the ORDER entity may represent a reference to an existing customer.

So we asked:

> **Can FORGE understand identity-related requirements declaratively and generate identifiers that obey uniqueness, stability, and key semantics?**

---

# 2. What did we actually test?

The experiment covered the identity vocabulary:

```text
PRIMARY_KEY
FOREIGN_KEY
UNIQUE
COMPOSITE_KEY
COMPOSITE_ID
NATURAL_KEY
SURROGATE_KEY
SEQUENTIAL_ID
UUID
STABLE
```

We then tested several different identity behaviors.

### Sequential identity

For example:

```text
CUS-1
CUS-2
CUS-3
CUS-4
```

### UUID identity

Values should be unique identifiers rather than simple sequential values.

### Stable identity

The same logical identity should remain stable under the defined generation semantics.

### Composite identity

Identity can be formed from multiple fields rather than a single field.

For example:

```text
CUSTOMER_ID + PRODUCT_ID
```

could collectively identify a record.

### Uniqueness

The generated values must not collide where `UNIQUE` is specified.

### Primary-key semantics

A primary key should have the expected identity properties.

# 4. What does that actually mean?

The important shift here is:

> **FORGE now understands that some fields have identity semantics rather than simply value-generation semantics.**

For example:

```text
CUSTOMER_ID
```

can be understood as:

```text
IDENTITY
+
UNIQUE
+
PRIMARY_KEY
+
SEQUENTIAL
```

rather than simply:

```text
STRING
```

That distinction becomes critical when we start generating related entities.

---

# 5. Why is this important?

Imagine we eventually generate:

```text
CUSTOMER
```

with:

```text
CUSTOMER_ID
CUS-1
CUS-2
CUS-3
```

and then:

```text
ORDER
```

with:

```text
ORDER_ID
CUSTOMER_ID
ORDER_VALUE
```

The second `CUSTOMER_ID` is not an independent random string.

It needs to refer to an existing customer.

So the conceptual model becomes:

```text id="s1g9os"
CUSTOMER
   │
   │ PRIMARY_KEY
   ▼
CUSTOMER_ID
   ▲
   │ FOREIGN_KEY
   │
ORDER
   │
   └── CUSTOMER_ID
```

020-G establishes the identity vocabulary and semantics needed for that later relationship work.

---

# 6. An important result: FOREIGN_KEY is still a boundary

Notice this:

```text id="b3d0kp"
FOREIGN_KEY boundary    PASS
```

That is actually good.

We don't want FORGE to pretend that generating a foreign key is equivalent to generating a random identifier.

A foreign key has a stronger requirement:

> **The generated value must correspond to an existing identity in another entity.**

That requires relationship resolution.

So 020-G establishes:

```text
FOREIGN_KEY
    ↓
Recognized vocabulary
    ↓
Identity semantics understood
    ↓
Relationship generation handled separately
```

That separation is architecturally healthy.

---

# 7. What did we learn?

The important lesson is:

> **Identity is a first-class generation concern, not merely a field type.**

These are fundamentally different:

```text
CUSTOMER_CODE
STRING
```

and:

```text
CUSTOMER_ID
STRING
PRIMARY_KEY
UNIQUE
STABLE
```

The underlying type may be identical, but their semantics are completely different.

This means the declarative specification is becoming richer:

```text
Field
 │
 ├── Type
 ├── Population
 ├── Generation strategy
 ├── Distribution
 ├── Identity semantics
 └── Constraints
```

That is much closer to what we need for real enterprise data generation.

---

# 8. Why did field-order independence matter here?

This also connects directly to 020-E.1.

Identity generation must not accidentally depend on the order in which fields are declared.

The experiment confirmed:

```text id="m4o3b1"
Field-order independence: PASS
```

So we now have consistency between:

* normal field generation
* population behavior
* identity generation

and the deterministic architecture established earlier.

---

# 9. What have we NOT proven?

This experiment establishes identity semantics, but it does **not** yet prove full relationship generation.

We have not yet proven:

* foreign keys resolve to actual parent records
* referential integrity across entities
* one-to-many relationships
* many-to-many relationships
* relationship cardinality
* orphan prevention
* relationship distribution
* composite foreign keys
* cross-entity dependency planning

Those are substantially more complex.

And importantly, **we shouldn't pretend that `FOREIGN_KEY` passing here means referential integrity is solved.**

It means FORGE correctly recognizes and safely handles the capability boundary.

The actual relationship generation needs its own experiments.

---

# 10. Architectural Outcome

The generation architecture is now becoming:

```text
                    FIELD
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
   Population      Identity       Generation
       │              │              │
       ▼              ▼              ▼
   Should exist?   Who am I?       What value?
                      │
              ┌───────┴────────┐
              ▼                ▼
          Primary Key      Foreign Key
              │                │
              ▼                ▼
         Identity          Relationship
```

This is a useful architectural boundary.

Identity generation and relationship resolution are related, but they are **not the same thing**.

---

> **FORGE can declaratively represent and generate identity-bearing fields, including sequential IDs, UUIDs, stable identities, natural and surrogate keys, composite identities, uniqueness, and primary-key semantics, while explicitly treating foreign-key resolution as a separate relationship capability.**
