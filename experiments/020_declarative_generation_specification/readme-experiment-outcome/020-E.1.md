# Experiment 020-E.1: Deterministic Field Stream Isolation

## 1. What were we trying to prove?

### In simple terms

020-E showed that FORGE could generate complete records, but there was a problem:

> Changing the order of fields changed the generated values.

That happened because fields were sharing a sequential random stream.

For example, imagine:

```text
Seed = 42

Generate A → consumes random numbers 1, 2
Generate B → consumes random numbers 3, 4
Generate C → consumes random numbers 5, 6
```

If we reorder the fields:

```text
Generate C → consumes random numbers 1, 2
Generate A → consumes random numbers 3, 4
Generate B → consumes random numbers 5, 6
```

The results change.

That is not desirable for a declarative specification.

So we asked:

> **Can each field have its own deterministic random stream so that one field's generation does not depend on the order in which other fields are generated?**

---

# 2. What did we actually do?

We introduced the concept of **field-level deterministic streams**.

Instead of giving every field the same random stream, FORGE derives a separate stream from the master seed and field identity.

Conceptually:

```text id="g0u5b1"
                 Master Seed
                     42
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
      FIELD_ALPHA  FIELD_BETA  FIELD_GAMMA
          │           │           │
          ▼           ▼           ▼
       Stream A     Stream B     Stream C
```

The experiment derived independent seeds for:

```text id="c9y31p"
FIELD_ALPHA
FIELD_BETA
FIELD_GAMMA
FIELD_DELTA
FIELD_SEQUENCE
```

Each field therefore gets its own deterministic generation context.

---

Everything passed.

**Overall: PASS**

---

# 4. What does that actually mean?

In simple terms:

> **FORGE can now make a field's generated values depend on the field itself, rather than on where the field happens to appear in the specification.**

So if we have:

```text id="8f0zqj"
CUSTOMER_ID
CUSTOMER_SCORE
CREDIT_LIMIT
```

and later rearrange them:

```text id="akp7we"
CREDIT_LIMIT
CUSTOMER_ID
CUSTOMER_SCORE
```

the fields retain their own deterministic generation streams.

The specification's ordering no longer accidentally changes the random numbers assigned to each field.

---

# 5. Why is this important?

This is more than a random-number implementation detail.

It establishes an important property of the **declarative model**.

A declarative specification should describe **what** we want, not accidentally introduce behavior based on the order in which the configuration happens to be written.

We want:

```text id="qj0tpu"
Same specification semantics
        +
Same seed
        ↓
Same generated values
```

even when irrelevant ordering changes.

That gives us a much stronger form of determinism.

---

# 6. There are now two kinds of determinism

This experiment helps us make an important distinction.

### Reproducibility

Same:

```text
Specification + Seed
```

produces the same result.

020-E already showed this.

### Order-independent determinism

Same:

```text
Specification semantics + Seed
```

produce the same result even when independent fields are reordered.

020-E failed this.

020-E.1 now passes it.

So we have moved from:

```text id="50k2b4"
Deterministic
```

to:

```text id="5w1q7p"
Deterministic
+
Order independent
+
Stream isolated
```

That is a much stronger property.

---

# 7. What did we learn?

The important architectural lesson is:

> **Randomness must be scoped to the thing being generated.**

Instead of:

```text id="y2a9yc"
Master RNG
    │
    ├── Field A
    ├── Field B
    ├── Field C
    └── Field D
```

we now have:

```text id="j5a6j8"
Master Seed
    │
    ├── Field A stream
    ├── Field B stream
    ├── Field C stream
    └── Field D stream
```

This also gives us a foundation for more advanced generation later.

For example, we can eventually have deterministic namespaces for:

```text
FIELD: CUSTOMER:CUSTOMER_SCORE
FIELD: CUSTOMER:CREDIT_LIMIT
ENTITY: CUSTOMER
RELATIONSHIP: ORDER:CUSTOMER
SCENARIO: PREMIUM_HEAVY
```

without making unrelated generation behavior interfere with each other.

---

# 8. Why is "field identity sensitivity" important?

The experiment also checked that different fields do not accidentally receive the same stream.

That means:

```text id="d2jz4g"
FIELD_ALPHA ≠ FIELD_BETA
```

even when they share the same master seed.

This is important because otherwise two unrelated fields could accidentally produce correlated or identical sequences simply because they were generated from the same random state.

---

# 9. What about sequential fields?

The experiment also tested:

```text id="e8a1sa"
FIELD_SEQUENCE
```

and confirmed:

> **Sequential field behavior remains stable under the new stream model.**

That matters because sequential identifiers are deterministic for a different reason than statistical fields.

For example:

```text id="9w8f9n"
CUS-1
CUS-2
CUS-3
CUS-4
```

should remain stable even though the random stream architecture has changed around it.

---

# 10. What have we now proven?

Together, 020-E and 020-E.1 give us a stronger statement.

### 020-E

> Multi-field generation worked, but field declaration order affected deterministic results.

### 020-E.1

> Field-level stream isolation removes that dependency and provides reproducible, order-independent generation.

So we can now say:

> **FORGE can provide deterministic field generation whose results are isolated from unrelated field execution order.**

That is a meaningful architectural foundation.

---

# 11. What have we NOT proven?

We should not overextend the result.

This experiment does not yet prove:

* dependency-aware randomness
* relationship generation
* cross-entity generation
* correlated statistical generation
* constraint-conditioned generation
* scenario-specific streams
* complete dataset reproducibility
* statistical quality of generated data

Those come later.

In particular, once fields **depend on other fields**, we need something more than independent streams.

For example:

```text id="xg4az7"
CUSTOMER_SCORE
      │
      ▼
CREDIT_LIMIT
```

Here `CREDIT_LIMIT` legitimately depends on `CUSTOMER_SCORE`.

The architecture therefore needs to distinguish:

```text
Independent fields
        ↓
Independent streams

Dependent fields
        ↓
Dependency-aware generation
```

That is exactly where the later dependency-planning experiments become important.

---

# 12. Architectural Outcome

The generation architecture now evolves to:

```text id="7hsgxi"
                 Master Seed
                     │
                     ▼
             Deterministic Context
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
      Field A     Field B     Field C
       Stream      Stream      Stream
          │          │          │
          ▼          ▼          ▼
       Generate    Generate    Generate
```

with an important rule:

> **Independent field generation must not depend on field declaration order.**

This becomes a core determinism property of FORGE.

> **FORGE can derive isolated deterministic generation streams for individual fields, providing reproducibility, field-order independence, field identity sensitivity, and stable sequential generation.**
