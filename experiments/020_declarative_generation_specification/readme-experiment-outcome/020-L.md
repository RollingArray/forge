# Experiment 020-L: Declarative Derived and Conditional Generation

## 1. What were we trying to prove?

### In simple terms

Real datasets contain many fields that should not be randomly generated.

For example:

```text
SUBTOTAL = QUANTITY × UNIT_PRICE
```

or:

```text
NET_AMOUNT = SUBTOTAL - DISCOUNT
```

or:

```text
IF CUSTOMER_TYPE = PREMIUM
THEN CREDIT_LIMIT = higher range
ELSE CREDIT_LIMIT = normal range
```

The important question is:

> **Can FORGE understand these relationships from the specification, determine what must be generated first, and calculate the dependent values correctly?**

The architecture tested was:

```text
Specification
      ↓
Expression analysis
      ↓
Dependency extraction
      ↓
Generation planning
      ↓
Context-aware generation
      ↓
Validation
```

---

# 2. What did we test?

The experiment covered two important classes of behavior.

### Derived / formula fields

For example:

```text
id="1j8f3p"
QUANTITY
    +
UNIT_PRICE
    ↓
LINE_AMOUNT
```

where:

```text
LINE_AMOUNT = QUANTITY × UNIT_PRICE
```

### Conditional generation

For example:

```text
CUSTOMER_TYPE = PREMIUM
        ↓
higher CREDIT_LIMIT
```

The generator therefore needs to understand the condition and select the appropriate generation behavior.

# 4. What does this actually mean?

The key result is:

> **FORGE can now distinguish between fields that need to be generated and fields whose values should be derived from previously generated context.**

That is a major difference.

Consider:

```text
QUANTITY = 5
UNIT_PRICE = 100
```

FORGE should not independently generate:

```text
LINE_AMOUNT = 723.42
```

Instead:

```text
QUANTITY
    = 5

UNIT_PRICE
    = 100

       ↓

LINE_AMOUNT
    = 500
```

The value is determined by the specification.

---

# 5. Multi-level derivation is especially important

The experiment also passed:

> **Multi-level derivation**

That means the dependency chain can extend beyond a single calculation.

For example:

```text
QUANTITY
   +
UNIT_PRICE
   ↓
SUBTOTAL
   -
DISCOUNT
   ↓
NET_AMOUNT
```

The engine must understand:

```text
QUANTITY ─────┐
              ├──> SUBTOTAL ───> NET_AMOUNT
UNIT_PRICE ───┘                   ▲
                                  │
                              DISCOUNT
```

It cannot calculate `NET_AMOUNT` until the required upstream values exist.

This is where the dependency planning from K.2 becomes directly reusable.

---

# 6. Why this is a significant architectural result

We now have three different kinds of field behavior:

### Independent generation

```text
CUSTOMER_SCORE
       ↓
Generate
```

### Constraint-driven generation

```text
CUSTOMER_SCORE
       ↓
Constraint
       ↓
CREDIT_LIMIT feasible region
       ↓
Generate
```

### Derived generation

```text
QUANTITY
     +
UNIT_PRICE
     ↓
LINE_AMOUNT
     ↓
Calculate
```

These are fundamentally different operations.

FORGE is beginning to model them separately rather than treating everything as "generate a random value."

---

# 7. Conditional generation adds another layer

Consider:

```text
CUSTOMER_TYPE = PREMIUM
```

The specification may say:

```text
IF PREMIUM
THEN CREDIT_LIMIT >= 5000
ELSE CREDIT_LIMIT >= 1000
```

FORGE now needs to:

1. generate or resolve `CUSTOMER_TYPE`
2. evaluate the condition
3. select the appropriate branch
4. generate `CREDIT_LIMIT`
5. validate the result

The experiment confirms:

```text
Conditional generation:       PASS
Conditional branch semantics: PASS
```

So the conditional mechanism is functioning as part of generation rather than merely as a validation rule.

---

# 8. Field-order independence passed again

This is particularly valuable because derived fields naturally create dependencies.

Suppose the specification lists:

```text
NET_AMOUNT
DISCOUNT
SUBTOTAL
QUANTITY
UNIT_PRICE
```

The generator must not blindly process that order.

It needs to infer:

```text
QUANTITY
   ↓
UNIT_PRICE
   ↓
SUBTOTAL
   ↓
DISCOUNT
   ↓
NET_AMOUNT
```

The result:

> **Field-order independence: PASS**

confirms that the dependency model is doing its job.

---

# 9. Cycle blocking is essential

Derived expressions can create cycles.

For example:

```text
A = B + 10
B = A - 10
```

There is no legitimate starting point.

The experiment explicitly tested cycle safety:

> **Cycle blocking: PASS**

This means the dependency graph is not only being used for execution. It is also being used as a safety mechanism.

---

# 10. Derived values are deterministic

Another important result:

> **Derived values are deterministic: PASS**

That means if:

```text
QUANTITY = 5
UNIT_PRICE = 100
```

then:

```text
LINE_AMOUNT = 500
```

should remain `500`.

Changing the random seed may change the upstream values, but the formula itself must behave deterministically.

This gives us an important separation:

```text
Randomness
    ↓
Input generation

Deterministic expression
    ↓
Derived output
```

That's exactly the behavior we want.

---

# 11. Division safety passed

This is a small but important engineering detail.

A formula such as:

```text
RATE = AMOUNT / QUANTITY
```

must not silently produce garbage when:

```text
QUANTITY = 0
```

The experiment confirms:

> **Division safety: PASS**

So expression evaluation has appropriate safety boundaries.

# 12. What did we learn?

The key architectural learning is:

> **Derived and conditional fields should be treated as dependency-driven generation nodes rather than ordinary fields.**

The architecture is becoming:


This is much closer to a real execution engine.

---

# 13. What have we now proven?

I would capture the capability as:

> **FORGE can declaratively generate conditional and derived fields by analyzing expressions, extracting dependencies, planning execution order, and evaluating formulas deterministically, while safely handling cycles, field-order variation, and invalid arithmetic operations.**

That is a strong capability statement.

---

# 14. What have we NOT proven yet?

We should still be careful.

L proves derived and conditional generation, but not yet their interaction with all the other capabilities.

We have not yet fully established:

* derived fields combined with statistical relationships
* derived fields constrained by feasible regions
* cross-entity derived fields
* scenario-specific formulas
* complex dependency graphs combining relationships and formulas
* statistical distributions conditioned by derived values
* large-scale performance

Those are addressed progressively later in 020.

And this is where **020-N.1** becomes particularly relevant, because it extends the same dependency/context model across entity boundaries.
