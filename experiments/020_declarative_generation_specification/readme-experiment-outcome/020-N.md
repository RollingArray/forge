# Experiment 020-N: Full Declarative Generation Integration

## 1. What were we trying to prove?

### In simple terms

By this point FORGE can independently demonstrate:

* specification validation
* generic field generation
* deterministic streams
* population and nullability
* identity generation
* relationships
* dependency planning
* constraint-driven generation
* derived fields
* conditional generation
* statistical generation

So N asks the natural next question:

> **Can all of these capabilities work together to generate a complex multi-entity dataset?**

The intended pipeline is:

```text id="n1v8q2"
Specification
      ↓
Vocabulary validation
      ↓
Capability assessment
      ↓
Expression analysis
      ↓
Constraint analysis
      ↓
Dependency planning
      ↓
Field generation
      ↓
Identity / relationship resolution
      ↓
Final validation
```

The integrated entities were:

```text id="3p8w2k"
CUSTOMER
CUSTOMER_PROFILE
PRODUCT
ORDER
ORDER_ITEM
SHIPMENT
```

That is much closer to an actual enterprise-style dataset.

# 3. Why this failure matters more than 020-K

020-K failed because one capability was not mature.

N fails because **integration itself is not yet solved**.

This is a much deeper architectural issue.

We have:

```text id="9q2m7v"
A works
B works
C works
D works
...
```

but:

```text id="w5k3p1"
A + B + C + D + ...
        ↓
   does not yet work
```

This is a classic systems problem.

Individual components can pass their own tests while the interfaces between them remain incorrect.

# 6. This is the key architectural lesson

We have built several specialized engines:

```text id="g8q3m1"
Field Generator
Constraint Engine
Expression Engine
Statistical Generator
Identity Generator
Relationship Resolver
Dependency Planner
```

But N is exposing the fact that they don't yet share a sufficiently strong common execution model.

We need something closer to:

```text id="0z8n4p"
                    Generation Plan
                         │
                         ▼
                 Execution Context
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       Generated      Constraints    Statistics
        Context        Context         Context
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                  Field Resolution
                         │
                         ▼
                 Entity State
                         │
                         ▼
              Relationship Resolution
                         │
                         ▼
                    Validation
```

Every stage needs to consume and produce a **shared, explicit generation context**.

# 8. The most important thing NOT to do

I would strongly recommend that we **do not simply patch each failing test until N says 16/16 PASS**.

That would risk turning N into a giant collection of special cases.

Instead, we should first identify the architectural failure.

The question should be:

> **What contract does every generation capability need to satisfy so that they can participate in one unified generation execution model?**

That is a much more valuable question.

# 9. What I think N is telling us

Based on the sequence we've built, I would investigate these areas first:

### 1. Shared generation context

Every generator needs access to:

```text id="7v5k1m"
Current entity
Current record
Previously generated fields
Parent entities
Relationship context
Scenario
Seed
Constraint context
Statistical context
```

Without this, the individual capabilities will work in isolation but fail together.

### 2. Field resolution state

A field should have an explicit state such as:

```text id="m9k2p4"
UNRESOLVED
   ↓
PLANNED
   ↓
GENERATING
   ↓
RESOLVED
   ↓
VALIDATED
```

This becomes especially important for:

* derived fields
* statistical relationships
* cross-field constraints
* foreign keys

### 3. Dependency graph needs to include more than entities

Earlier we primarily established:

```text id="2m7x5p"
ENTITY A → ENTITY B
```

But N needs something closer to:

```text id="3s8q1v"
CUSTOMER.CUSTOMER_SCORE
          ↓
CUSTOMER.CREDIT_LIMIT
          ↓
ORDER.ORDER_VALUE
          ↓
ORDER.DISCOUNT
          ↓
ORDER.NET_AMOUNT
          ↓
SHIPMENT.SHIPPING_COST
```

That is a **field-level execution graph across entities**.

This is probably the bigger architectural evolution N is asking for.

---

# 10. Why primary keys and relationships fail together

This is worth investigating carefully.

If:

```text id="0p8q3m"
Identity generation
```

and:

```text id="z5v2n8"
Relationship resolution
```

both passed independently but fail in N, then the likely issue is not the individual identity generator.

It may be that the integrated generator isn't preserving the identity context correctly between stages.

For example:

```text id="q7m4x1"
CUSTOMER generated
     ↓
CUSTOMER_ID exists
     ↓
ORDER generated
     ↓
ORDER.CUSTOMER_ID needs CUSTOMER_ID
```

The relationship resolver needs to see the actual generated identity registry.

This suggests that N is testing the **interface between identity generation and relationship resolution**, rather than those components individually.

---

# 11. Why derived fields fail too

The same pattern applies here.

020-L proved:

```text id="8s1m4p"
ORDER_VALUE
     ↓
DISCOUNT
     ↓
NET_AMOUNT
```

can work in its own controlled context.

N adds:

```text id="4q9n2m"
CUSTOMER
   ↓
ORDER
   ↓
ORDER_VALUE
   ↓
DISCOUNT
   ↓
NET_AMOUNT
```

Now the derived field depends on values that themselves depend on:

* relationships
* statistical generation
* constraints

So the dependency graph needs to cross capability boundaries.

That is likely the central integration problem.

That is a deeper architectural requirement.

---

# 13. Why reproducibility fails

This is especially important.

Earlier experiments proved reproducibility independently.

N says:

```text id="f4k9p1"
Reproducibility: FAIL
```

That tells us that combining multiple generation mechanisms is changing the random-stream behavior.

That is a major finding.

We need to ensure that:

```text id="2w6n8r"
Field identity
+
Entity identity
+
Scenario
+
Master seed
```

deterministically define the generation stream.

Otherwise adding another field or changing generation order can unexpectedly change existing values.

This connects directly back to **020-E.1**.

The field-stream isolation architecture needs to survive the full integrated execution model.

---

# 14. What did N actually teach us?

I would summarize the architectural finding as:

> **FORGE has validated its individual declarative generation capabilities, but the first attempt to compose them into a complex multi-entity generation pipeline exposed an integration gap around shared execution context, cross-capability dependencies, and deterministic state propagation.**

That is the correct conclusion.

Not:

> "FORGE doesn't work."

And not:

> "We just need to fix 13 tests."

The architecture needs another layer.

---

# 15. This is probably the most important experiment so far

Ironically, the **3/16 PASS** result may be more valuable than several of the 16/16 experiments.

Why?

Because N is the first experiment asking:

> **Does the architecture survive complexity?**

And it says:

> **Not yet.**

That gives us a concrete research/engineering problem to solve.

# 16. What I would do next

I would **not jump directly to O** yet.

Before moving forward, I would introduce an integration-hardening experiment, something like:

### 020-N.1

**Unified Generation Context and Execution State**

Purpose:

> Establish a common execution context that allows field generation, identity resolution, relationships, constraints, statistics, derived values, and conditional generation to share deterministic state.

The architecture would be:

```text id="2j7q9p"
Specification
      ↓
Capability assessment
      ↓
Unified generation plan
      ↓

      ↓

      ↓
Context-aware generation

      ↓
```

Then test the interfaces individually:


# 17. What success should look like

The goal isn't merely:

```text
16/16 PASS
```

The real success criterion should be:

> **The same declarative specification produces a valid integrated dataset regardless of entity order or field order, while preserving identity, relationships, constraints, statistical behavior, derived values, reproducibility, and capability boundaries without post-generation repair.**

Then N becomes a genuine integration gate.

That's the finding I would preserve.
